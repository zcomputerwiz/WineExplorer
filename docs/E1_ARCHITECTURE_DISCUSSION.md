# E1 architecture discussion

Static design review, 2026-11-06. This discussion reads docs/ELEVATION_ROADMAP_FIT.md, docs/ELEVATION_BOUNDARY_PLAN.md, docs/ELEVATION_BROKER_WORKORDER.md, docs/ELEVATION_CONSENT_WORKORDER.md, docs/ELEVATION.md and src/programs/wexelevate/main.c. It does not establish installed-system acceptance. No builds, execution tests or network research were performed. Local code observations below are verified by inspection of that broker; reports about other components are attributed to the supplied documents and are unverified here. External mechanisms and historical examples are recalled public knowledge, unverified against current primary documentation in this review. The named reading destinations are research pointers, not citations claiming a fresh source check. No proprietary implementation material is used.

The owner's settled direction is loud denial on failure, broker ownership of authorization and token creation unless this comparison justifies changing it, filtered-administrator click consent first, administrator credentials for standard users later, and best-effort presentation and request integrity with explicit limits. A visible error and no surviving process or request handle is the intended failure contract. Best effort describes the strength of the supported boundary; it must not turn a detected failure into permission to run. Scripts, interpreters and DLLs remain stated limits.

## 1. Concept comparison and recommendation

### Windows, conceptually

The public UAC model separates the requesting application, a trusted elevation service running as SYSTEM, and a consent process presented on a secure desktop. A filtered administrator normally runs with a restricted token. The corresponding full administrator token is associated with the same authenticated logon. Approval lets the trusted service start a new process with that linked full token; it does not let the requesting application give itself arbitrary administrator rights. Token construction and access enforcement ultimately belong to the operating system's trusted security machinery. The elevation service obtains and assigns an authorized token rather than manufacturing an arbitrary identity from a dialog response.

The consent process gathers the user's answer. The service owns the policy decision and validates the request and answer before launch. Conceptually that includes authenticating the requester and its security context, applying elevation policy, resolving the target, presenting program identity and publisher information, associating the answer with that pending request, and choosing the correct user, logon and session token. A standard-user credential prompt authorizes a different administrator identity; it is not the standard user's token with an administrator flag added. The exact internal validation order, IPC fields, image-opening flags and object lifetimes vary or are not publicly specified; they are unverified here and must not be invented as a model for our code.

The secure desktop isolates the real prompt from ordinary application window messages and injected input within the operating system's security model. It does not make application-provided descriptions truthful, prove that arguments are harmless, or freeze every file the eventual program can load. Public UAC guidance distinguishes an administrative convenience boundary for an administrator's split tokens from stronger security boundaries between users and privilege levels. The exact current vendor security-servicing classification is unverified here. We should state our own guarantees rather than infer them from UAC branding.

Publicly discussed bypass classes include policy-dependent automatic approval of trusted programs, those programs acting on user-writable configuration or associations, DLL and executable search-path hijacking, argument or environment influence, deceptive prompts, and file or namespace changes between inspection and use. File races can involve reparse or symbolic links, directory replacement and writable dependencies. These are classes to investigate, not a claim that a particular current Windows version has an unfixed main-image swap flaw. Some historical attacks require an administrator's filtered token and a permissive prompt policy; others are actual memory-safety or authorization defects. They should not be conflated. No generic public guarantee that a displayed path, a signature and an eventual launch are one immutable transaction is assumed here.

For us the useful pattern is service-owned authorization, a broker-owned prompt, a linked token selected from trusted identity, and a new process. Automatic approval lists are unnecessary risk for E1. All supported requests should require click consent, including trusted signed programs.

### Our broker as authority

The proposed authority stays in wexelevate. The machine-root broker image is root-owned and the system-role launch chain establishes its privileged Wine identity. Root ownership of the image does not mean the broker runs with host UID zero. The supplied work orders describe the same Unix user, a protected system role, and retained wexsys group access for elevated programs. A Windows SYSTEM token, a host root identity and the right to modify the machine root are distinct authorities.

The broker already identifies a named-pipe caller through wineserver, compares the pipe impersonation identity with the opened process token, accepts the limited elevation type, freezes the request and asks its own consent child. It retrieves the caller's linked full primary token and creates the target. In this division, wexelevate decides whether that request is authorized and requests token use; wineserver remains the trusted issuer and enforcer of Wine token objects. Saying that the broker owns token creation is an architectural ownership statement, not evidence that main.c synthesizes tokens itself.

Trust anchors include the system-role launcher, protected broker and prompt images and their libraries, wineserver and the Wine loader actually used, machine-root ancestors and permissions, service configuration, protected enforcement policy, and the host kernel enforcing Unix permissions. Image ownership alone is insufficient if an ordinary user can replace a parent directory, redirect the loader to another builtin image, change a loaded library, or turn enforcement off. An elevated installer already allowed to modify the trusted machine tier is inside this administrative trust domain; E1 cannot simultaneously authorize arbitrary machine administration and protect the broker from that administrator.

An ordinary local authenticated Wine client may request elevation over the named pipe, but it must not select its own SID, administrator identity, token or approval result. The client must authenticate the broker endpoint against the trusted service instance; the broker's first-instance pipe protection alone does not authenticate it to clients. That client check is reported in the broker work order, not verified in the client source here. Only the broker-created consent process for that request supplies its answer. Starting a separate look-alike dialog confers no authority. The Unix support calls currently exposed through wexhost are image-lease plumbing, not a separately authenticated privileged authorization service.

The advantages are a small first-release component set, direct access to Wine process and token objects, existing real target-handle semantics, and one owner of request freezing, cancellation and launch. Click consent needs neither a system bus nor an authentication agent. The design fits the existing per-session system role and avoids translating a host authorization result back into a Wine token for the first release. It is straightforward to exercise parser failures, A/B consent isolation and launch cleanup in disposable Wine fixtures.

The disadvantages are a larger trusted Wine-side code path and reliance on wineserver's token, process, registry, desktop and transport enforcement. The supplied documents explicitly exclude complete defense against native same-UID attacks on this compatibility boundary. The root-owned broker cannot compensate for an untrusted server or loader. Host-wide audit and policy are less centralized. Restart recovery and multi-session routing are project responsibilities. Tests using a prompt hook demonstrate orchestration, not trusted physical input or host isolation.

Each request must bind the host UID, stable process identity, Wine SID, logon/authentication identity, wineserver instance, machine root, session and target desktop. A username or numeric PID alone is insufficient. A live process handle pins the process after it is opened, but does not close the earlier PID-query-to-open reuse interval. The current broker checks the user SID and repeats the pipe PID query; it does not explicitly compare logon or session identity. This is a real binding limitation even when PID reuse would yield the same user. First-release multi-session support should be limited to independently bound per-session brokers, with no shared global approval channel.

On restart all uncommitted approvals must die; a new broker instance must never recover permission from a surviving dialog's zero exit status or an old request ID. The server should invalidate the old broker generation and restore input. Graceful stop must cancel pending work. An already committed target is different from an uncommitted launch, but the lifetime of any promised image protection must be independent of accidental broker shutdown or must end that target. The current lease design does not provide that guarantee on broker death.

### Host-side privileged wexhost mechanism with D-Bus and polkit

This alternative introduces a genuine host-side privileged mechanism, distinct from the current wexhost DLL bridge and from a polkit authentication agent. The host mechanism accepts authenticated requests over the system bus, freezes the authorization subject and request, obtains a polkit decision, and authorizes a narrow execution operation. The Wine broker executes only that operation. Polkit makes a policy decision about a subject and action; it does not itself create a Wine token or execute the Windows application.

Token creation still needs a trusted wineserver bridge. Either the host mechanism directs that bridge to issue the exact token or it authorizes the broker to retrieve an already identified linked token. Token selection cannot be left to unauthenticated client metadata. If the broker retains unrestricted power to launch with full tokens, the host mechanism is an intended policy authority but a compromised broker can still bypass it. Removing that bypass requires server-side enforcement of host-issued, single-use authorization or another constrained execution interface. That adds work beyond placing a D-Bus call before the existing launch.

The trust anchors become the host mechanism and its dependencies, kernel and system bus credentials, polkit rules and authority, the authentication agent and credential backend when used, session mapping, and the still-trusted Wine execution bridge. Ordinary bus clients may submit requests only under kernel-derived peer identity. The mechanism must map that peer to the actual Wine caller through a trusted channel; a Wine PID, SID, session string or prefix path supplied over D-Bus is not proof. Conversely, authorizing the privileged mechanism's own root subject would authorize the deputy, not establish the original caller's entitlement. The polkit subject and policy must intentionally represent the requester's identity and session, with action details derived by the mechanism.

Only the trusted mechanism may send executable approvals to the broker. A grant must bind both component generations, caller and session, frozen target identity and hash, command line, cwd, environment policy, expiry and a single-use nonce. Connection-bound server state can avoid a portable bearer token; a public request ID or a successful polkit call from another client cannot be a grant. Bus ownership changes, mechanism death, broker death, disconnect and expired requests invalidate pending grants. Never use retained blanket authorization for arbitrary elevation.

Advantages include a host-owned policy and audit boundary, established polkit administrator policy and agent integration, better potential isolation from untrusted Wine clients, and a natural future home for multi-user identity mapping and credential workflows. A native mechanism can use host process descriptors and file descriptors directly. A machine-wide daemon can survive an individual Wine session while explicitly cancelling that session's requests. Its request and policy logic can be tested separately from Wine.

Disadvantages are more privileged IPC, more trusted components, bus and agent availability failures, duplicate request state across processes, and a difficult host-to-Wine identity mapping. A host prompt is not automatically the right secure desktop for a Wine session. Host restart and Wine restart can leave half-completed launches unless both share a precise transaction protocol. An authorization Boolean does not reveal which administrator authenticated for a standard user. Integration tests need real bus, polkit policy, agents, credentials and multiple sessions in addition to Wine. A host authority is useful only if its enforcement boundary is real; the same-UID compatibility design does not become host isolation merely by adding polkit.

### Recommendation

Keep wexelevate as the authorization and token-use owner for E1 filtered-admin click consent. Reuse the existing system-role and wineserver foundation, with the narrow release contract in section 4. Do not add a second privileged authority solely to confirm a same-user click. Keep wexhost as necessary host-operation plumbing, without treating its name as proof of a daemon boundary. A narrow future credential interface can supply verified administrator identity without moving all first-release policy to the host.

Reconsider a host authority when over-the-shoulder identity mapping, centralized host policy or actual host isolation is being implemented. At that point explicitly decide whether the host decides and wineserver enforces its grants, or the broker consumes authenticated credential evidence and remains the decision owner. Two independent components must not each believe that the other authorized a request. Windows' conceptual service pattern supports the current choice; it does not prove our same-UID boundary has Windows' host security properties.

## 2. Request integrity options, ranked by simplicity and strength

There are three separate bindings: the bytes inspected for consent, the filesystem object opened at launch, and the bytes Wine eventually maps and faults in. A pathname names an object at a moment in a particular namespace. An open descriptor pins an object, not its pathname or immutable contents. Hashing describes bytes read, not execution atomicity. All options below bind the exact request parameters too; none makes an approved interpreter's arguments or dynamically loaded code safe.

Mount substitution is relevant only where an adversary can influence the namespace or mount view used by the broker or loader. Ordinary users do not automatically have authority to replace host mounts. User namespaces, imported mounts, drive mappings and deployment configuration determine whether that attack is reachable; their exact permissions are unverified here. Keep the broker and loader in the same trusted mount view, and do not treat a path resolved in a caller-controlled view as equivalent without checking it. The filesystem cases below describe residual mechanisms, not a claim that every ordinary caller can perform every substitution.

For additional engineering in this tree, the simplicity order is: first retain the existing deny-write/delete image handle; second hash that object before consent and recheck identity and hash before launch; third add a correctly scoped inotify watch if needed for native-write detection; fourth make signature verification authoritative against the frozen object; fifth stage and execute a protected copy. Existing publisher UI may make signature display cheap, but robust verification, trust-store and offline policy are separate work. The existing read lease is already implemented and can be retained rather than replacing it with a new watcher, subject to its lifecycle limits below.

For main-image integrity, the strongest listed construction is a protected staged copy actually used by Wine for execution, followed by a held object with real mutation exclusion and execution bound to that object. Within Wine's sharing rules, deny-write sharing provides useful prevention; against native host writes it does not. A watch plus held object and rehash provides detection below actual exclusion. Rehash alone is weaker. An ordinary open handle alone only pins identity. Signature checking is orthogonal, not a comparable race lock. There is no honest total strength order between a Wine-only lock and a host watch without specifying the attacker and filesystem.

### Held open handle with deny-write and deny-delete sharing

The cheapest baseline is to open the target for reading before consent, allow read sharing only, retain it through consent and launch, and reject conflicting pre-existing opens. This closes ordinary cooperating Wine write, truncate and delete/replacement access to that file while the sharing checks apply. A second identity check must verify that the launch path still names the held object. The current broker does both a held open and a later reopen by path.

It does not generally pin parent directory names. Renaming a parent directory, swapping an ancestor symlink or replacing a bind mount can redirect the launch path while the original handle still refers to the original inode. Deletion restrictions on the leaf do not freeze the namespace. A native hardlink aliases the same inode; writes through it change the held object unless host-level mutation exclusion also applies. Whether Wine sharing checks cover every alias consistently is unverified here. Unix native writes do not honor Wine share modes. An existing writable mapping, changed ACLs or a remote writer must not be assumed excluded by merely holding a descriptor.

NFS and 9p require explicit validation of sharing, caching and object identity behavior. A retained handle on either is not a portable Windows-style lock. Unsupported or unknown filesystems should be denied for E1 rather than advertised as protected. In Wine, the decisive remaining gap is that process creation reopens the path and may select a builtin image or another loader route. The handle is not currently passed as the executable image object. Even a perfect lock on the original inode does not stop a path from leading to another inode after the final verification.

An fd-based launch of the exact pinned object would close namespace substitution of the main image; it still needs stable bytes. Holding the handle only until process creation also leaves later lazy reads from mutable backing storage. Retain protection until the executable mapping is independently immutable, or document and enforce a longer lifetime. That mapping property is unverified for this release.

### Hash at consent and re-hash at launch

Compute SHA-256 from the held object before presentation, then reopen the path and compare stable file identity, size, timestamps and hash immediately before launch. Compare the held object again too. This cheaply detects persistent in-place changes, hardlink writes, leaf replacements, parent renames, bind-mount redirection and symlink swaps when they change the object or bytes visible at the second check. Matching inode metadata is useful evidence, not a replacement for the hash. Hash the entire target with an explicit resource budget; exhaustion is an error.

The race remains between the final open/hash and Wine's actual image open, and between that open and later reads. A change-and-restore between checks is invisible. Without a real lock or snapshot, a writer can race the hash itself, so the read need not represent one coherent version of the file. File IDs can be reused or have weaker semantics across mounts; mount identity matters in addition to device/inode-like values. A symlink, ancestor or mount can be switched again immediately after verification. A hardlink provides the same in-place mutation path as the original name.

On NFS or 9p a re-read can observe caches rather than remote changes with the timing assumed locally. Hashing twice does not fix remote-server trust or cache coherence. Hashing one file while Wine loads a builtin twin also proves the wrong artifact. This is a useful E1 check combined with the held handle and an explicit local-filesystem scope, not an atomic launch guarantee.

### Inotify watch

Install watches before computing the consent hash, then establish and verify the opened object's identity. Watch the file for modification, close-write, attribute, move-self and delete-self events; watch the relevant directory entries for replacement and movement. Deny on a relevant event, watch invalidation, unmount, queue overflow or inability to establish coverage. Drain events and recheck the object and path before committing. The initialization sequence must deny if it cannot determine whether a change happened while watches were being installed. Merely watching the leaf pathname after hashing leaves an initial blind interval.

An inode watch can detect local writes through hardlinks because they affect that inode. Directory watches help detect leaf symlink swaps and rename operations within watched directories. Watching only the immediate parent misses a renamed ancestor. Covering arbitrary ancestor renames, drive-map changes and mount topology requires additional identity checks and namespace controls; it is no longer a small leaf watch. Bind-mount replacement is not reliably covered as an ordinary watched-file mutation. Watching a symlink itself and watching its resolved target are different operations, and neither freezes the entire resolution chain.

Inotify reports changes after they occur; it does not hold off the writer or loader. An event can arrive after the final queue drain and before or after the target starts. Some memory-mapped writes and remote changes are outside the notification behavior one might assume. NFS server-side changes and 9p behavior must not be treated as reliable local notifications; details are unverified here. Event overflow is loss of evidence and must mean denial, never a clean file. Wine's actual opened image, including builtin resolution, must still match the watched object.

This meets the owner's best-effort watch alternative if the residual event-delivery and final-launch windows are accepted and stated. It does not satisfy a literal promise that no changed byte can ever execute. For this tree, replacing the existing kernel lease with inotify is not automatically simpler: ancestor coverage, event lifecycle and overflow handling are new work. Prefer retaining a sound existing lease on supported mounts; use a watch only as a deliberate weaker profile, never an automatic fallback when stronger protection fails.

### Copy, then run from a root-owned staging file

Use an already protected local staging directory, create a new file exclusively without following a destination symlink, copy from the held source descriptor with size limits, finalize the staged bytes, and remove ordinary-user write access before consent. Hash and inspect the staged object; display the original location and clearly identify that the approved bytes are a staged copy. Consent must approve that copy, not a source hash calculated before a mutable copy operation. If a source change is detected during copying, deny; otherwise the staged hash is the authoritative identity of what will run.

If Wine truly loads the staged object through protected ancestors in a controlled mount namespace, later renames of the original parent, original bind-mount changes, original hardlink writes and original symlink swaps cannot replace those staged bytes. Reading from NFS or 9p becomes an import operation, not ongoing reliance on remote executable pages. It does not make the remote source trustworthy; it gives consent a fixed local object to approve.

The destination must have no attacker-writable hardlink or surviving writable descriptor, and all ancestors, mount topology and loader selection must be trusted. A root-owned file in a user-writable directory, a user-controlled bind mount over staging, or a Wine path redirected elsewhere defeats the construction. Read-only mode bits are insufficient if the attacker owns the file and can change them. Copying into a shared wexsys-writable directory also needs a precise threat model about already elevated administrators. Wine builtin selection must be checked rather than inferred from the staging pathname.

This changes the program location. Relative DLLs, resource lookups, sibling executables, self-updaters and installer self-location can fail or load different dependencies. Scripts can still name external interpreters and data. A genuinely root-owned staging facility is also not something the current same-UID broker can simply create by setting a mode: it needs a privileged helper or prearranged protected storage with a narrow creation protocol. Quotas, crash cleanup and per-request ownership are additional work. This is the strongest listed practical bytes-at-rest option, but too disruptive to be the default E1 installer path.

### Signature check

Verify the signature, signer chain and stated trust policy against the same frozen content whose hash is displayed and checked for execution. This supplies publisher/integrity evidence covered by that signature. It closes a misleading-publisher problem when the attacker substitutes unsigned or differently signed content before verification and the policy rejects it. It does not authorize elevation by itself, establish that the publisher's program is safe, or freeze the file.

Parent-directory renames, bind-mount substitution, hardlink mutation and symlink swaps can redirect execution after a path-based signature check just as after a hash. A held file plus execution binding is still required. On NFS or 9p the bytes verified must be the same coherent bytes eventually loaded; a trust result does not fix filesystem semantics. Wine loading a builtin twin or external dependency also remains outside a main-file signature check. Signature coverage need not be identical to a raw whole-file SHA-256 identity; retain the whole-file hash independently.

For an offline first release, do not claim live revocation knowledge. Define cached/offline chain behavior and label unknown or unverifiable publishers accurately. An invalid signature must not produce a verified publisher label; whether to allow click consent for it, like an unsigned file, is an owner policy question. Verification errors caused by inability to read or bind the frozen image are request-integrity failures and deny. The existing dialog's path-based publisher check is reported by the work order; its exact parser and trust behavior are unverified here.

### The existing Linux read lease

The supplied consent work order describes host fcntl read leases taken before hashing, a break monitor, and retaining the lease until the elevated process exits. This is stronger than Wine sharing alone for local native write opens, including opens through hardlinks to the leased inode. It rejects an existing writer or an unsupported writable filesystem. A read lease neither pins ancestor directories nor makes a new pathname open use the leased inode. An attacker can substitute another object that has no lease. Never describe the lease as closing that final path-selection race.

The work order records a launch-to-arm interval, a possible wineserver blockage while a writer waits on the lease, eventual kernel lease-break timeout, termination of only the elevated process rather than its descendants, and loss of protection when the service stops. These are unverified in the lease implementation here, but main.c confirms asynchronous post-creation arming and guard ownership. Keeping this mechanism for E1 avoids a new watcher implementation, but its current lifetime behavior cannot support an unconditional fail-closed claim. Do not silently fall back to weaker checks on lease failure. If the intended guarantee is only protection during consent and launch, say so explicitly and address later Wine image reads separately.

## 3. Prior art to borrow and where to look

These are named public primary-documentation and advisory destinations for later verification. All external details in this section are unverified in this offline review. Version-sensitive features and exact advisory applicability need checking before implementation. Names refer to public services, interfaces and projects, not proprietary source files.

Polkit and pkexec: look at the polkit reference manual, its Authority, Subject and AuthenticationAgent interfaces, action definitions, rule documentation, and upstream security advisories. Borrow separation of mechanism, policy authority and prompt agent; authenticated subjects; cancellation; and authorization scoped to one operation. pkexec history includes CVE-2021-4034, an argument-handling memory-corruption class involving an empty argument vector and environment influence, and polkit history includes CVE-2021-3560, involving identity handling around a disappearing D-Bus client. Older pkexec subject/PID race advisories, including CVE-2011-1485, are another reading target; the exact mechanics and version ranges are unverified here. The lessons are to bound and validate every IPC field, fail on missing identity, pin subjects against PID reuse, and treat disconnects as cancellation. A call to pkexec does not bind our PE image or manufacture the correct Wine administrator identity. Cheap now: these boundary rules. Later: a real polkit credential integration with authoritative chosen-administrator evidence.

Sudo and sudoedit: look at the sudo and sudoers manuals for command digests, fd execution where available, environment rules and sudoedit restrictions, together with sudo's upstream security advisories. Borrow opening and identifying the command object, minimizing inherited environment and descriptors, and refusing unsafe link/path conditions. sudoedit's temporary-copy and validated-copy-back model illustrates how much care is needed around writable directories and symlink swaps; it is not directly an executable-launch solution. CVE-2023-22809 concerns sudoedit argument/environment influence; CVE-2015-5602 is a symlink/path handling reading target, with exact race mechanics unverified here. Do not collapse all sudo history into filesystem races: memory-safety and policy matching failures are separate classes. Cheap now: immutable request fields, descriptor ownership and explicit environment policy. Later: a general race-resistant directory traversal or copy-back framework.

Systemd-run and run0: look at upstream systemd manual pages for transient units, systemd-run and run0, plus service credentials, execution environments and process lifecycle controls. They offer a trusted service manager launching a scoped job with explicit identity and cleanup rather than giving a long-lived application an ambient elevation switch. run0's availability and exact authentication behavior are version-dependent and unverified here. Neither supplies Wine tokens, a Wine process handle or our secure-desktop session mapping. Cheap now: one owned launch transaction, explicit environment and supervisor-backed lifetime. Later: use of transient host units and cgroups if a host mechanism is introduced. They are not drop-in E1 launchers.

macOS Authorization Services and SecurityAgent: look at Apple's public Authorization Services programming material, authorization-right definitions, privileged-helper guidance and SecurityAgent descriptions. Borrow the separation between a right being granted, a trusted prompt agent and a privileged mechanism consuming that right. A prompt agent's display role is not the authority to perform arbitrary operations. Rights caching and transferred authorization objects must not become reusable arbitrary-program approval here. Exact present-day platform support, APIs and deprecations are unverified. Cheap now: operation-specific rights, request-bound answers and no passwords in our UI. Not cheap: reproducing that platform's trusted agent infrastructure.

Windows UAC and the public AppInfo service behavior: look at Microsoft Learn's UAC architecture and process, Admin Approval Mode, elevation prompt policy and secure desktop documentation, and public access-token documentation. Borrow the SYSTEM elevation service, separate consent process, same administrator's linked full token and a new elevated process, as described conceptually in section 1. Public security guidance and vendor advisories are the appropriate place to verify bypass classifications and policy qualifications. Do not infer an undocumented descriptor-based launch protocol or universal TOCTOU guarantee. Cheap now: click every supported request and no automatic approval by signer or path. Not cheap: matching the host platform's entire desktop, token and application compatibility model.

Flatpak portals and xdg-desktop-portal: look at the XDG Desktop Portal API documentation for request objects, request closing, caller-associated handles, parent-window association and the document portal. Borrow per-request lifetime, cancellation on caller loss, an agent displaying trusted request data, and capabilities for specific resources rather than broad permission. Session-bus identity is useful but not a replacement for the host UID and Wine session binding needed here. A caller-supplied parent-window identifier is presentation metadata, not authorization. Cheap now: these request lifecycle rules. Later: portal-style capability and document mediation if resource-scoped operations replace arbitrary elevation. A portal alone does not confer administrator rights or trusted secure input.

Android and iOS consent models: look at Android's public runtime permission, system permission-controller and package identity documentation, and Apple's public privacy permission and entitlement documentation. Borrow narrowly named permissions, clear identity, cancellation, trusted system presentation and distrust of application-drawn approval. Those systems generally authorize capabilities within an app sandbox, not unrestricted desktop administrator execution. App identity is supported by a package and installation trust model we do not have for arbitrary loose PE files. Cheap now: plain explanation of the action, no remembered blanket Yes, and no application-supplied publisher assertions. Not cheap: a comparable package identity, entitlements and sandbox ecosystem.

Linux fanotify with FAN_OPEN_EXEC_PERM: look at the Linux man-pages documentation for fanotify, fanotify_init, fanotify_mark and fanotify permission events. The attractive idea is kernel mediation before an executable open proceeds, rather than after-the-fact notification. Privileges, filesystem and mark support, queue overflow, daemon failure and event-response behavior require explicit policy; do not assume monitor death denies execution. The key Wine caveat is that PE files may be ordinary data opens and mappings by the Wine loader, while the host executable event concerns Wine itself. Whether any relevant PE path generates the needed event is unverified and likely cannot be assumed. Cheap now: nothing beyond borrowing the distinction between prevention and notification. Not suitable as an E1 shortcut without loader analysis and filesystem acceptance work.

Fs-verity and IMA: look at Linux kernel fs-verity and integrity subsystem documentation, userspace verity tooling, and IMA measurement/appraisal policy documentation. Fs-verity can make enabled file contents read-only and verify reads against a digest; a trusted expected digest or signature policy is still needed to identify approved content. It does not freeze parent names or ensure Wine chose that file. IMA measurement records evidence; appraisal can enforce policy where configured hooks and trust roots cover the actual access. Whether PE loading is appraised as desired is unverified. These require filesystem/kernel provisioning, key and policy management and an import/update story for arbitrary downloads. Cheap now: content hashes as identity. Later: verity-backed staging or managed machine images, not a first-release requirement.

Memfd, execveat and execution from an opened fd: look at the Linux man-pages entries for memfd_create, fcntl file seals, execveat and fexecve. Borrow stable object references and, for memfd, seals that prevent writes, resizing and further removal of the chosen restrictions. An fd alone permits content mutation; sealing must be complete and all writable aliases accounted for. Executing from an fd avoids re-resolving the original filename for the host executable. It does not automatically make the PE loader consume that fd; executing Wine from an fd pins Wine, not the approved PE. Interpreter handling, descriptor inheritance and original-path semantics also need care. Cheap now: preserve the opened-object identity in the request. Later: a Wine loader contract that accepts a pinned or sealed PE image, with compatibility work for original location and dependencies. That is the most direct way to close our final main-image path race, but is not implemented by main.c.

For E1, borrow request binding, stable identity, no approval cache, strict parsing, bounded waits, endpoint authentication, deliberate environment rules and supervisor-backed cleanup. Reuse the existing handle, hashes and supported local lease path. Avoid a new global execution monitor, integrity subsystem, staging daemon or credential stack just to add filtered-admin consent. Those larger mechanisms should be selected for a concrete later guarantee, not as decorative security dependencies.

## 4. Concrete first-release proposal and owner questions

### Components and supported boundary

Use the existing protected launcher/system-role foundation and wineserver, one wexelevate service per bound Wine session, its existing host lease support, and one broker-owned consent process at a time per interactive session. No new D-Bus mechanism or polkit dependency is needed for filtered administrators. Serializing prompts is simpler than several overlapping authoritative windows on one secure desktop; requests may queue under bounded limits. Queue expiry is part of the same request deadline.

Support a provisioned, enforcement-enabled machine root, a filtered administrator with a genuine linked full token, an explicitly bound active interactive session, and validated local filesystem types for mutable images. Use the Wine secure desktop for the prompt. The supplied boundary plan reports X11 restrictions and physical-input harness results but also native same-user X11 access; Wayland compositor isolation remains a gap. These are not fresh test results. A dimmed snapshot is cosmetic. On an unimplemented or failed presentation backend, deny with a visible explanation; do not fall back to ordinary-desktop consent. Best effort means the accepted X11 native-client limitation remains documented, not that switching or input-grab failures are ignored.

For image integrity, retain the deny-write/delete handle, whole-file hash, immediate identity/hash recheck and current local read lease where required. Keep the held file through consent and launch; retain the lease through the lifetime promised by the chosen mapping policy. Do not add inotify as an automatic fallback. This is a simple continuation of existing code, with a candid residual final-path race. If the owner requires elimination of that race, E1 needs descriptor-bound PE loading or protected staging first. Neither an existing lease nor an extra rehash justifies claiming it eliminated.

### Exact authorization and launch checks

1. Establish the trust configuration before accepting requests. Verify system-role SYSTEM identity and enabled trusted token authority; require protected service, broker, prompt and loader paths and policy. Confirm enforcement cannot be disabled by a limited caller. Authenticate the client-visible service endpoint. Missing provisioning, unknown policy, corrupt policy or unsupported session/backend denies. Default to click consent and secure desktop. Reject any configuration requesting no prompt, automatic elevation, credentials or ordinary-desktop consent in this release. The current code accepts an explicit ordinary-desktop policy; the proposal deliberately narrows that behavior.

2. Read one bounded, versioned request from an authenticated local connection. Check magic, version, exact message size with overflow-safe arithmetic, every length limit, known flags and an allowed show state. Reject embedded string terminators and malformed environment blocks. Treat image, command line, cwd and environment as untrusted data; the separate absolute image field determines the executable, not the first command-line word. Preserve the command line exactly rather than assuming a universal Windows argv parser. Reject unsupported device paths, ambiguous drive-relative paths and special files. Normalize and resolve under the intended Wine drive mapping, preserving the requested location for display and recording the resolved identity. Do not run a shell or search PATH for the target.

3. Bind the authenticated pipe peer to a stable wineserver process object before trusting a numeric PID. Acquire the process and effective security identity atomically with connection attribution, or refuse the unsupported case. Match host UID, Wine user SID, logon/authentication identity, wineserver instance, machine root and session. Reject a request from an impersonation context differing from the bound primary identity. Require a live filtered-administrator token, its proper limited shape and a linked full token of the same user and logon/session. A standard user receives unsupported without collecting credentials. An already full-token caller uses the ordinary non-broker launch route; this broker must not reinterpret it as a fresh consent case.

4. Allocate an immutable request record under bounded total, per-caller and per-session quotas. Record the process reference, token, resolved image, exact command line, cwd, environment policy and contents, display session, expiry and broker generation. Generate a request identifier with a cryptographic generator; deny if generation fails. The ID is a correlation value, not a bearer authorization credential. Bind any internal approval channel to the broker-owned process and request object. The current entropy fallback is unsuitable for a promised random ID, even though the current table also checks request object identity.

5. Open a regular disk image with read access and read sharing only; keep the handle. Check that the caller has the intended right to request this image, so the broker cannot expose privileged-only files through display, hashing or copying. Record object identity and available host mount identity. Acquire required mutation protection before hashing. For the current lease route, an existing writer, unsupported mount, uncertain ACL/writeability test or failed monitor setup denies. The documented lease exemption for files the caller cannot write needs confirmation that aliases, ACLs and later permission changes cannot invalidate the assumption within the supported boundary. Capture SHA-256 and metadata after protection is established; deny any instability. Confirm Wine will load the inspected PE rather than another builtin or redirected object, or reject that unsupported target class.

6. Determine publisher status from the frozen object and bind that result to its hash. Never verify by reopening an unbound path and then display that publisher as the identity of other bytes. Unsigned or unavailable offline trust information is displayed accurately. A corrupt read or inability to bind metadata denies. Show the application identity, original and resolved location where different, publisher/signature status, and the full command line with a digest available in details. Escape untrusted text, handle Unicode controls without misleading labels and never silently truncate. Program labels and icons are descriptive data, not authorization evidence. If a target is an interpreter, identify that fact and state that scripts and loaded dependencies are outside the main-image check.

7. Create or authenticate the secure desktop for this session using the trusted server role, with a restrictive descriptor and no inherited handles. Verify desktop switching and the available host presentation/input setup before accepting input. Start the protected consent implementation explicitly as the broker's SYSTEM child on that desktop, with bounded frozen display data and no target-controlled environment or cwd. Only its own request-bound result can approve. Never accept a client-provided helper exit code or a separately launched prompt. Serialize presentation and keep queued requests invisible until their own turn.

8. Wait for consent together with caller death, disconnect/cancellation, service stop, session loss, integrity break and an absolute request deadline. Default to denial. A known approval result is necessary but not sufficient: recheck all cancellation and integrity conditions immediately before committing because several events may be signalled together. Cancel or close yields cancellation; timeout, unavailable prompt, unsupported policy and integrity failure remain distinct errors. Terminate and reap the prompt on abort, restore input, revoke its request record and release resources. If the prompt cannot be reaped or input cannot be restored, escalate visibly to the trusted session supervisor; do not declare clean cancellation while assuming cleanup worked.

9. Consume the request exactly once under synchronization and recheck the live caller and bound token/session. Reopen the image path and compare it and the held object with the frozen identity, metadata and SHA-256. Recheck lease state and any protected namespace assumptions. Revalidate policy at commit or define an atomic policy snapshot with explicit revocation behavior; for E1, a newly observed deny or policy change cancels. Reject a changed drive mapping, symlink resolution, mount identity or parent path when detectable. Document that a subsequent change before Wine's final path open remains possible. This residual cannot be repaired by labelling the record immutable.

10. Obtain the linked primary full token only from the bound trusted token object. Verify user, logon/session, full elevation, administrator groups and intended integrity/Unix group mapping; never select a token from a SID or username in the request. Start with the target user's default Windows environment, unless an explicitly supported inherited-environment policy is frozen and shown. The broker and host loader use only trusted host environment state. Allowing an application-controlled Windows environment is a compatibility choice with dependency-injection limits, not a sanitization guarantee. Use a validated absolute cwd. Do not create privileged directories from arbitrary environment strings or follow unchecked profile links; provision trusted profile/temp directories through a narrow anchored operation.

11. Prepare rollback before target code is runnable. Create the child suspended, with no inherited handles, the fixed executable image and intended caller parent/desktop. Attach it to server-owned cleanup containment and arm image protection before resuming. The server must know the pending child's ownership from creation, so broker death in the creation-to-registration interval cannot orphan it. Whether existing Wine job and server facilities can supply these exact semantics is unverified and needs a design/implementation check; suspension alone is not enough. If creation, containment, token validation, protection arming or handle duplication fails, terminate and reap the suspended child, close any remote handle in the caller's handle table, and return an error with zero pid/tid/handle. No executable code may run merely because creation succeeded before a later setup failure.

12. Complete an explicit launch commit, then resume exactly once and return only a real target handle with wait and limited-query rights if requested. Define the commit at a trusted server state transition, with client-visible outcome tied to that state. Failure before commit rolls back. A transport failure after commit must not be represented as proof that nothing ran, and must not cause an automatic retry. If the product instead requires cancellation on lost delivery, the supervisor must revoke the child and remote handle on that path, while acknowledging that already executed effects cannot be undone. The current one-reply pipe protocol cannot atomically guarantee both successful delivery to a possibly dying caller and the absence of all execution on any lost reply. This is an owner-visible semantic decision, not a detail to hide in an error code.

13. Keep a committed target's integrity guard and resources under explicit ownership until their promised lifetime ends. Under the current lease policy, a break requires terminating the protected target and waiting for death before releasing the lease; notify visibly. Descendants are not protected by killing only the parent. If request-tree termination is promised, enforce it through trusted containment, including broker death. Graceful stop cancels pending requests and either preserves committed protection in a surviving supervisor or terminates the affected processes before releasing it. Restart invalidates every pending grant and old prompt; it never silently replays a launch. Cleanup must restore the correct session input desktop, not another user's desktop selected from a global name.

14. Report failures visibly through the requesting shell or a trusted session-level fallback if the caller is gone. Return distinct cancellation, timeout, unsupported, policy, integrity, startup and resource errors, with no success-shaped pid/tid/handle on a rejected launch. Record bounded audit metadata: requester/session, request generation, image identity and hash, decision, error and launch commit. Command lines and environment may contain secrets; do not log them wholesale by default. Normal success may leave a running target and an intentional caller handle; the no-process/no-handle rule applies to rejected or rolled-back requests, not completed authorized launches.

### Gaps visible in the current broker

The main-image handle, hash, metadata recheck, caller process reference, request table, bounded approval wait, SYSTEM-owned consent child and restricted returned handle are useful foundations. Several historical claims in the supplied docs are obsolete for this code: missing administrator policy now selects click consent, the secure desktop defaults on, and there is real filtered-admin approval. Standard users remain unsupported. The old caller-owned helper-exit-code launch diagram and password-verification claim in docs/ELEVATION.md must not be treated as the current architecture.

The final image launch is still by pathname: verify_image closes its reopened check handle, then launch uses the path again. The read lease protects the original inode, not a substituted target. There is no explicit host mount/session binding in the request structure. identify_caller compares SIDs and repeated PIDs but does not pin the connection's original process atomically or compare logon/session IDs. random_id falls back to time/thread/address-derived data on generator failure. Multiple consent windows can be active. An explicit secure-desktop policy of zero selects the ordinary desktop. These are static observations, not reproduced attacks.

launch creates a runnable target before duplicating its handle and arming its lease. If DuplicateHandle fails, the error is retained but the target is not terminated on that path. If lease arming or guard allocation fails, termination is attempted without waiting for confirmed process death. On a reply error, client_thread closes the returned handle value in the broker's own handle table even though that value belongs to the caller; it is not a valid remote-handle rollback operation. Reply delivery errors are ignored, and the subsequent pipe flush is outside the bounded pipe_io wait. Thus current error handling cannot support the owner's no-survivor contract. This deserves correction before broader acceptance regardless of the selected integrity profile.

stop_event is waited during approval, but is not checked again as an explicit final launch gate. If approval and cancellation become ready together, the prompt result can win the wait; later caller and lease checks do not cover every service/session cancellation. Guard threads are not counted as active request threads for service shutdown, and the work order explicitly reports losing running-process leases when the service stops. Broker crash cleanup is not established by main.c. The broker restores input on its normal service exit; crash recovery is reported as a server backstop by the boundary plan and is unverified here.

Publisher inspection is not present in main.c: the broker passes the frozen path and command line to the UI, which the work order says performs its own publisher check. Whether that check uses the same object and cannot be redirected is unverified. The current temp-path validator checks a drive prefix and some backslash-delimited parent traversals; it does not visibly establish anchored traversal, reject all path aliases or prevent symlink redirection. A token-derived environment path alone is not proof that every filesystem component is trusted. No change to that code was made in this review.

### Acceptance evidence to obtain later

Future implementation acceptance should cover real approval and denial, caller death, disconnect, prompt crash, broker stop/crash, session loss, image mutation and replacement, parent rename, symlink and mount substitution, writable hardlink aliases, existing writers, unsupported mounts and simultaneous approval/cancellation. Exercise handle duplication, guard allocation, entropy and transport failure after child creation, plus broker death at each launch transition. Verify that a rejected request leaves no runnable child, prompt, duplicated caller handle or leaked lease, and restores real input. Test two users and two sessions, independent A/B approvals, 32/64-bit callers and the actual Wine builtin/file selection path. Actual pixels and physical input need installed-session evidence. These are proposed checks; none was run for this discussion.

### Open questions for the owner

1. Is the residual main-image namespace race acceptable for the first best-effort release, with held handle, hash and lease but path-based Wine launch? If it is not, choose descriptor-bound PE loading or protected staging as required work before release. The existing lease is insufficient to claim that race closed.

2. Should image protection last through target exit, as the current lease design intends, or only through an explicitly defined immutable image-mapping point? The latter point is unverified. Should a later integrity break or broker death end the entire elevated process tree? The current policy ends only the target and drops protection on service stop.

3. What is the user-visible commit contract when the caller or reply channel dies during launch? Recommend a server-recorded commit with no automatic retry and rollback before commit. A literal guarantee that every lost reply means nothing ever executed is not achievable through a single pipe reply after starting code.

4. Which initial local filesystems and interactive session configurations are supported? Recommend explicitly validated local mounts and the documented X11 best-effort boundary first, denying NFS, 9p and other unvalidated executable sources and unsupported presentation paths. Define whether simultaneous sessions are independently supported or explicitly refused pending identity-binding work.

5. May E1 consent to unsigned images and images with invalid or offline-unverifiable signatures when labelled accurately? Recommend allowing unsigned/unknown publisher click consent, no signer-based automatic approval, and a deliberate separate rule for invalid signatures. Read/binding failures still deny.

6. Which environment and cwd compatibility is necessary for installers in E1? Recommend default target-user environment, a validated absolute cwd and provisioned private temp directories. Decide whether caller-supplied Windows environment is an explicit supported option with dependency limits.

7. When standard-user credentials are added, should the broker remain the policy owner consuming authenticated administrator evidence, or should a host authority issue wineserver-enforced grants? Either path needs an authoritative administrator identity, trusted UID/SID/logon mapping and matching host execution rights. A polkit authorization Boolean or a username typed into the dialog is insufficient.

These questions refine the release contract; they do not reopen the settled decisions to deny loudly, start with filtered-admin secure-desktop click consent, or document best-effort presentation and dependency limits.
