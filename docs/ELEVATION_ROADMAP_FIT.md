# Elevation consent: roadmap fit

Static assessment, 2026-11-05. Sizes are relative engineering estimates (S: days, M: one to several weeks, L: multiple weeks); risks include unknown integration and validation work, not delivery commitments. This assessment does not run a build, installer, guest or security test.

## Current state

T3 is **partial**, but its 2026-10-18 overview is older than subsequent boundary work. `docs/ELEVATION.md:5` and `:226` correctly warn against claiming production completion, but their statement that filtered-admin consent is only designed does not describe the later broker. Likewise, the helper-exit-code diagram and PAM/password claim at `docs/ELEVATION.md:38` and `:97` are historical, not the current design. The fork copy `wine/programs/consent` no longer exists; `src/programs/consent` is the owned source (`docs/STOCK_CHANGES.md:479`).

With the configured helper **and** launcher-backed system role, the later implementation has a SYSTEM `wexelevate` broker, request freezing and image lease, a linked-token launch and process handle, and broker-owned `consent.exe` click approval for filtered administrators (`src/programs/wexelevate/main.c:4`, `:14`, `docs/ELEVATION_BOUNDARY_PLAN.md:183`, `docs/STOCK_CHANGES.md:1098`). The X11 Winlogon desktop has server restrictions, a dimmed snapshot and input grabs; its harness includes real host input and attack/cleanup cases (`docs/ELEVATION_BOUNDARY_PLAN.md:174`, `scripts/test_sysrun_server.sh:1113`, `:1195`). These are reported work-order/harness results, not a current installed-image acceptance claim. The old comment that the shipping broker always has no consent at `scripts/test_sysrun_server.sh:594` describes an earlier test case; policy 2/5 now launches the real dialog (`:1098`).

Standard users and credential policies remain unsupported, and a broker without the system role fails closed (`src/programs/wexelevate/main.c:20`, `:502`, `:912`; `src/programs/consent/consent.c:562`). The D-Bus/polkit mechanism, authenticated administrator identity mapping and request-bound credential authorization are design work, not demonstrated implementation (`docs/ELEVATION.md:181`, `:196`, `:218`). The same-user Wine-token seam is not by itself host privilege isolation (`docs/ELEVATION.md:175`). `wex-sysrun` is a fixed-program setgid launcher, not that daemon (`tools/wex-sysrun/wex-sysrun.c:2`, `:22`, `:355`). Helper-unset operation preserves stock behavior, so image provisioning and enforcement are material (`docs/ELEVATION_BOUNDARY_PLAN.md:253`).

## Dependencies and placement

Recommend a new **open track E1 — Production elevation and installer authorization**, immediately before and co-scheduled with “Future: stock browser installers” (`docs/ROADMAP.md:257`), without renumbering completed phases. Give E1 release-blocking priority for supported machine installs and ISO acceptance; preserve the roadmap's DWM-first scheduling for already committed visual milestones, but do not defer E1 behind all DWM/DComp/Wayland work. Secure Wayland presentation depends on the relevant compositor security work; DComp and browser sandbox work can proceed independently (`docs/ELEVATION_BOUNDARY_PLAN.md:246`).

```text
system-role launcher + protected machine root + enforced helper + token/broker foundation
  ├─> isolated filtered-admin test approval ─> Chrome MSI/stub + Edge MSI diagnosis
  └─> E1 trust/identity decision ─> broker + polkit credentials + secure presentation
                                      ├─> interactive machine installers / broad app compatibility
                                      └─> installed-image and ISO release acceptance
Wayland compositor security ──────────────> Wayland interactive E1 acceptance
future shared session-0 / HKLM model ─────> U1 machine-wide registration design
browser COM/service fixes ────────────────> browser installer acceptance and related U1 Wine changes
U1 inventory + Windows-host fixture ──────> can start independently
```

The present per-session system role is a prerequisite for the implemented broker; the **future shared system tier/session 0 is not** a prerequisite for delivering E1. Design the backend to migrate to that model, whose cross-user wineserver and single HKLM are separate work (`docs/ROADMAP.md:240`). U1 explicitly schedules machine-wide registration after the system-tier model, while inventory and its host fixture can start now (`docs/uwp/README.md:19`). Package installation may need elevation when it changes machine state, but do not make all per-user U1 work depend on E1 or ISO completion.

Browser elevation is a gate, not the only defect. The provisioned standard-user Chrome MSI exited before `DoInstall` (`docs/CHROME_INSTALLER_ANALYSIS.md:1064`); earlier unprovisioned runs lacked the system role and cannot establish the same failure under SYSTEM (`:1042`). Edge's handoff and Chrome updater/COM failures are separately recorded (`docs/BROWSER_INSTALLER_TEST_PLAN.md:188`). Re-run unmodified installers after correct provisioning and approval before assigning remaining service/DACL or COM causes; success requires install, launch and functional fixture (`docs/ROADMAP.md:274`). Many other machine installers use the same authorization path, so E1 is a general Windows-app compatibility gate, not a browser-only feature.

## Lab-only automation

**Yes, conditionally:** the existing compile-time test approval is sufficient to advance automated installer diagnosis for a **filtered administrator** in a disposable, properly provisioned system-role guest, if the installer actually reaches the broker. It does not make the standard-user path work: the broker rejects that token independently (`src/programs/wexelevate/main.c:20`, `:356`; `scripts/test_sysrun_server.sh:1093`). Use a filtered-admin test account now; standard-user end-to-end tests require the real credential/identity work or a separately designed, explicitly scoped test identity fixture. A positive result establishes installer behavior under simulated approval, not interactive consent, credential authentication or security acceptance.

Reuse `scripts/test_sysrun_server.sh:643`–`:671` and `:925`–`:955`: compile separate `wexelevate_test.exe`/stub and `consent_test.exe` only in the harness, verify positive controls, check shipping binaries lack stub/hook strings, scan build/package inputs for both macros, and search installed trees for test artifacts. Restore the broker service and delete test binaries after the run (`:703`). Extend these checks to the actual staged root, packaged binaries, initramfs/ISO and final image, fail the image build on any hit, and independently inspect image contents; the existing searches do not by themselves prove every image is clean. No environment or registry switch should activate approval in production.

## Decisions before implementation

* **Authority and identity:** specify which privileged component owns authorization and Windows token creation, how kernel-derived D-Bus peer credentials bind to the wineserver caller and session, and how an authenticated administrator identity is obtained and mapped. `CheckAuthorization` success alone cannot supply the over-the-shoulder UID (`docs/ELEVATION.md:159`, `:218`). Define multiple users, sessions, reconnects, PID reuse and daemon restart behavior.
* **Request integrity:** bind authorization to one immutable request, image object and command/working directory/environment, not just a pathname or reusable approval; make displayed identity match executed content. Resolve scripts, interpreters, DLLs and mutable dependencies as well as the existing main-image lease; specify fail-closed lifetime and process-handle ownership (`docs/ELEVATION.md:196`, `docs/ELEVATION_BOUNDARY_PLAN.md:183`).
* **Trusted presentation:** decide whether policy permits a shared desktop, what native same-user X11 clients can do, and how Wayland compositor and polkit agent authenticate and isolate the prompt. Do not equate a Wine desktop DACL or cosmetic overlay with host-wide secure input (`docs/ELEVATION_BOUNDARY_PLAN.md:174`, `:181`).
* **Privilege scope:** document the distinction between Windows full token, Unix UID, saved `wexsys` group and shared machine permissions; ordinary users must not acquire reusable host privilege or choose their own privileged executable. Audit trusted launcher paths, groups, environment and setgid lifecycle (`tools/wex-sysrun/wex-sysrun.c:93`, `:355`; `docs/ELEVATION_BOUNDARY_PLAN.md:196`). Decide behavior for helper-unset/unprovisioned prefixes and ensure image defaults cannot silently bypass enforcement.
* **Failure and recovery:** specify policy defaults, cancellation versus timeout and service failure, authorization revocation, prompt and desktop cleanup after client/broker/compositor death, and no process/handle on failure. Validate all on installed X11 and Wayland, not solely with test hooks.

## Broker profile directory

The broker now creates the requesting user's TEMP and TMP directory chain in the machine root before the elevated launch. After the environment block is chosen, `launch()` reads `TEMP` and `TMP` (case-insensitive `env_lookup`) and, for an absolute path with no `..` component, creates each missing component from the root down (`ensure_dir_chain`), treating `ERROR_ALREADY_EXISTS` as success and ignoring other errors without failing the launch. This closes the product gap in `docs/GUEST_SYSROLE.md` step 7 (elevated `msiexec` ending 1627 after `GetTempFileNameW path not found`); both architectures compile cleanly. The guest test is still to be done with the lab broker `wexelevate_test.exe` per `docs/GUEST_SYSROLE.md` steps 7 and 8.
