Priority P0 = startup/communication or navigation dependencies to inspect first; P1 = important conditional rendering or correctness; P2 = lower/optional. “Required” describes the selected path, not a demand for every possible API to exist. All functional checks should use existing tests or a focused real PE/Windows comparison; none authorize execution in this audit.

## Dependency map and order

`browser → sandbox policy/token + startup attributes → suspended child + initial thread token → section/policy transfer → child LowerToken/handle cleanup → Mojo inherited pipe + IO completion + transferred sections → network service TCP → renderer receives response → GPU/ANGLE/Skia → presentation`.

The native Wine client↔wineserver control channel underlies many operations but is **not** a Chromium Win32 API. Its unexpected loss is the separately owned active investigation; no causal inference from this map. The best inspection order is (1) process/token and handle inheritance, (2) pipe endpoint connection and overlapped completion, (3) cross-process handle/section ownership, (4) handle-table/LowerToken policy if enabled, (5) real TCP connect/read/write, (6) selected EGL/D3D device, (7) presentation. Runtime has not identified which boundary failed, so ranking is triage, not a diagnosis.
