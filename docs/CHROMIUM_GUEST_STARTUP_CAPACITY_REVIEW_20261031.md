## Findings

1. Linux guest boot succeeds. All four recent serials reach SSH and login; r4 mounts ext4 read/write and later unmounts cleanly. No EXT4-fs error, I/O error, journal corruption or OOM-kill is present in these serials. Initial read-only root mount followed by read/write remount is normal in these traces. This does not prove complete filesystem integrity or rule out prior incomplete file copies. Wine initialization, rather than Linux boot, was what timed out.
2. Storage pressure is real: retained r4 inspection reports a 79G filesystem with 2.5G available before the private prefix; 1.6G available afterward. A fresh prefix consumes about 0.9G. A second prefix plus copies and logs can consume the reserve quickly. The latest retained r4 log does not itself show ENOSPC, and a timeout with space remaining does not identify a disk-caused wait. Inventory free bytes AND inodes and verify runtime completeness before further staging. Existing pressure warrants capacity work; it does not establish that a newly installed OS is needed.

Reuse the installed compositor and exact helper environment from the known successful browser run, with matched loader/server/modules, one fresh owned prefix and space for that prefix plus bounded logs. If initialization still stalls, collect thread-level wait/syscall evidence for the exact owned stalled processes using available tools; wchan=pipe_read across several Wine processes alone does not identify the upstream dependency.

In parallel, have the coordinator record df -B1, df -i and bounded directory usage for existing builds/prefixes/logs, and plan adequate guest AND host capacity. Favor preserving the installed guest and moving already archived evidence or expanding/cloning its disk under explicit coordinated ownership over another installation. A new overlay on the same full backing filesystem does not create guest filesystem free space; the partition/filesystem capacity or occupied content must actually change. If filesystem/package/runtime damage is demonstrated or recovery exceeds a bounded diagnostic attempt, prepare a clean replacement with sufficient capacity and only verified artifacts, preserving the old disk for comparison. No new VM is required by current evidence.
