## Actionable code review — not yet acceptable for integration

1. **Potential out-of-bounds read of registry data.** GetAppContainerFolderPath in dlls/userenv/userenv_main.c uses RegQueryValueExW into a fixed moniker buffer and checks only REG_SZ, not returned length, WCHAR alignment or terminating NUL, before passing that buffer to wide formatted string operations. A malformed/unterminated registry value can be read beyond valid data. The earlier accepted registration code deliberately checks these conditions. Validate the returned value and fail cleanly, with a focused malformed-value test.
2. **Unchecked filesystem failures and unsafe path construction.** Both AppContainerRegisterSid and CreateAppContainerProfile construct Packages paths from a caller-supplied moniker/name and ignore CreateDirectoryW errors; both treat any nonzero GetEnvironmentVariableW result as valid even when required size exceeds MAX_PATH. In the latter case the provided output buffer is not a usable returned path. Success can be reported after no directory was created; names containing separators/traversal can target unintended locations. Prove native contract for valid and invalid names, use bounded canonical owned paths and correct errors/rollback where required, avoid writing outside the intended Packages tree and preserve existing valid mappings/data. Do not silently create empty folders on arbitrary metadata-only registrations unless justified by actual native behavior.
3. **Delete mutates filesystem after failed unregister.** DeleteAppContainerProfile calls RemoveDirectoryW on name-derived directories even if AppContainerUnregisterSid failed or was missing. It may remove pre-existing empty directories after an error and maps missing registration to S_OK without native proof. Preserve data on failed/unowned operations and test exact relevant lifecycle against Windows.
4. **Sandbox evidence remains limited.** The token wrapper returning a handle and the process command line do not establish enforcement or native-compatible capabilities; existing test checks TokenIsAppContainer but does not test actual capability membership and effective access. CreateAppContainerToken passes TOKEN_ALL_ACCESS into NtCreateLowBoxToken; the actual source-handle rights/capability path needs a focused native-vs-Wine consumer test. Preserve the existing token stack; do not claim isolation from profile metadata.
