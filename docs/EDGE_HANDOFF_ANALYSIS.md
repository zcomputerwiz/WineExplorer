# Edge updater handoff: static investigation

The current evidence does not identify the failing Wine branch. The updater reports a failed ShellExecuteEx and HRESULT 0x80004005, followed by its own 0x80040708. ShellExecuteExW itself returns BOOL, not HRESULT; the log does not show the caller's conversion, GetLastError, hInstApp, verb, mask, directory, token, or actual DLL binding. In particular, 0x80004005 does not establish that Wine returned E_FAIL or ERROR_GEN_FAILURE. The earlier report of no `+exec` records is significant only after confirming that the channel was enabled in the actual updater process, both architectures and all inherited output were captured, and the loaded shell32 matches this source. `SHELL_execute` traces at entry, before its normal failure branches; absence of that entry under verified capture means this implementation was not entered, not merely that `SHELL_ExecuteW` was not reached.

The ranking below is an investigation order, not measured probabilities. The previous service `is machine: 0` observation predates the sysrun/fixed-rpcrt4 run and is not a token measurement. A working `/svc` or `/regserver` launch, or a successful ComSpec shell probe, does not prove the exact handoff has the same token, flags, image state or timing. Conversely, a non-SYSTEM service alone cannot explain a FALSE return from a separate updater's ShellExecuteEx without a demonstrated causal path.

1. **Call capture or failure outside the shown Wine shell implementation.** `ShellExecuteExW` in `wine/dlls/shell32/shlexec.c:2303` immediately calls `SHELL_execute`, whose first trace records mask, verb, file, parameters and directory. The updater may report a wrapper failure, call another binding/architecture, or have its trace routed elsewhere. Probe: enable `WINEDEBUG=+timestamp,+pid,+tid,+loaddll,+exec,+process` for the entire process tree, retain each process's stderr, and grep `MicrosoftEdgeUpdate`, `shell32`, `mask=`, `execute:`, `retval`, and `CreateProcessInternalW`, correlating PID/TID and time. Verify with a known ShellExecuteEx probe in the same environment. If the exact call still has no entry, capture the actual API entry/return with a debugger or a small intercepting test harness; record all `SHELLEXECUTEINFO` fields, BOOL, immediate GetLastError and hInstApp. This is a proposed future probe, not a test performed here.

2. **Image resolution or race at handoff.** `SHELL_FindExecutable` (842-1080) returns file-not-found if the explicit path cannot be resolved/exist, is inaccessible to the effective context, or exceeds its fixed path/result buffers; missing association/verb can also return `SE_ERR_NOASSOC`. `SHELL_execute` returns FALSE for a result <=32. The installed file existed for other launches, but not necessarily at the exact instant and in the handoff's effective context. Probe: `+exec,+file,+process`, grep the handoff PID for `SHELL_FindExecutable`, `Returning SE_ERR_FNF`, `xlpFile`, `returning path`, file open/status and `retval`. A tiny same-token probe should call GetFileAttributesW and CreateFileW on the exact path immediately before ShellExecuteExW, recording errors and timing, without reproducing private command-line data. Check the process and thread tokens separately. A positive existence check alone does not exclude a race.

3. **Process creation fails after resolution.** `SHELL_ExecuteW` (513-631) calls CreateProcessAsUserW with a NULL token for ordinary verbs; advapi32's export forwards to kernel32 and kernelbase's `CreateProcessAsUserW` delegates to `CreateProcessInternalW`. That function can fail while extracting the image name, allocating process parameters, or in `create_nt_process`/NtCreateUserProcess because of image, access, token, resources or server errors. The shell returns the Win32 error if below 32, but maps errors >=32 to `ERROR_BAD_FORMAT` as its shell result while preserving the captured last error. It does not unconditionally map every failure to bad format. Probe: `+exec,+process,+file,+server,+seh`, grep `Execute`, `CreateProcessInternalW`, target image, `CreateProcess returned error`, `returning`, and the relevant server reply/status; correlate thread IDs. A same-context harness can compare ShellExecuteExW with CreateProcessW using a writable quoted command line, capturing immediate errors. Avoid starting the actual installer in a generic probe: use a benign executable with equivalent path and manifest, then test the real target only in a controlled later reproduction.

4. **Elevation branch, conditional on verb, token and manifest.** `is_elevation_required` in `wine/dlls/kernelbase/process.c:525` returns true only when the helper setting is not absent/empty, token query and activation-context queries succeed, and the target requests requireAdministrator, or highestAvailable with a Limited token. It exempts Full, not every SYSTEM token: measure `TokenElevationType` rather than infer it from SID. `CreateProcessInternalW` then returns elevation required. In `SHELL_ExecuteW`, a configured helper routes this error to `execute_with_broker`; an invalid helper returns access denied with its error, and an unset helper maps the error to bad format. Explicit `runas` also invokes the broker when configured and `is_full_token()` is false; invalid configuration fails immediately; with no helper it tries `get_admin_token`. Ordinary open on a Full token does not enter the broker merely because the process is SYSTEM. Probe: `+exec,+process,+reg,+security`, grep `Elevation required`, `asking the elevation broker`, `broker returned`, `CreateProcess returned`, and the helper registry reads. A tiny probe logs process and effective thread TokenUser, TokenElevationType, integrity, impersonation level and linked-token query result, plus exact shell fields and immediate result. Inspect the actual target manifest and 64-bit-view helper value. Missing trace is not proof of a particular branch.

5. **Broker rejection or linked-token launch failure, only if branch 4 enters it.** `execute_with_broker` (449) fails if wexhost or its export is unavailable, command-image extraction fails, or `WexElevateRun` returns an error; it maps file/path/share/memory specifically and other errors to `SE_ERR_ACCESSDENIED`, preserving broker error. `src/programs/wexelevate/main.c:handle_request` rejects a missing system role and propagates failures from caller identification, request parsing, image freeze/verification, consent, lease, or launch. `launch` requires a linked primary Full token, builds an environment and uses CreateProcessAsUserW; it can fail on those operations or handle transfer. `wine/dlls/ntdll/unix/security.c` forwards TokenLinkedToken and duplication to wineserver, so client traces alone cannot establish server authorization. Probe: `+exec,+process,+security,+server,+service`, grep `broker returned`, `wexelevate`, `create_linked_token`, `duplicate_token`, and failing server replies for the correlated request; capture broker stderr too. If logs do not name the broker stage, use a minimal client invoking the same broker API and record its returned DWORD, then inspect server-side request diagnostics in a separately authorized instrumented run. Cancellation, unavailable service, bad linked-token type and image verification are distinct outcomes, not interchangeable evidence.

6. **Service identity or token setup affects the caller or broker.** `wine/programs/services/services.c:get_service_token` returns no account token when `system_role` is false, so the service is launched with the inherited identity; when true it requests a service token, fails for unsupported accounts or a failed `ProcessWineCreateServiceToken`, and service startup uses CreateProcessAsUserW with that token. Broker `handle_request` independently requires its SYSTEM role. A service launch failure can block the broker; an incorrect service identity could alter application behavior, but the updater's separate ShellExecuteEx failure is not shown to depend on its `/svc` process. Probe: `+service,+process,+security,+server`, grep `cannot start`, `failed to create process`, service name and token/server replies; use a tiny service or process-inspection probe to print actual TokenUser SID, elevation type, integrity, privileges and process ancestry for services.exe, updater caller and broker. Check sysrun role and service account configuration in the same run. Do not substitute the application's `is machine` message for token evidence.

7. **Other shell paths and resource failures.** `SHELL_execute` can return FALSE on failed environment expansion (`SE_ERR_OOM`) or, when `SEE_MASK_CLASSALL` selects the class route, on `SHELL_execute_class` association, command expansion, DDE or launch errors. ID-list translation and a supplied class/verb can alter resolution. These paths depend on fields not shown in the log; URL and directory fallbacks are not the normal route for the stated absolute executable. Context-menu handler failure normally falls through to ordinary resolution; a successful handler returns TRUE, not E_FAIL. Internal `shellex_run_context_menu_default` initializes an HRESULT to E_FAIL if no default menu item exists, but that internal value is not directly ShellExecuteExW's return. Allocation sites without checks may crash rather than return a clean error. Probe: the entry `+exec` mask and class/verb, followed by `SEE_MASK_CLASSNAME`, `SHELL_FindExecutableByVerb`, DDE, context-menu `invoke command returned`, and final `retval`; use a small same-context harness varying only the observed mask/verb and logging BOOL, hInstApp and immediate last error. Unchecked allocation/crash needs `+seh` or a debugger, not an assumption that it yielded FALSE.

The `RoGetActivationFactory` 0x80040154 lines identify missing WinRT classes, including telemetry and region-policy classes in the supplied logs. No static connection from those calls to the shell launch is shown; temporal proximity is insufficient, and the same telemetry message appears in later updater processes. Treat as a separate possible application-side prerequisite until an API trace or controlled comparison demonstrates that it changes the handoff. The `secur32:start_samss` and `load_auth_packages` errors likewise show authentication-package initialization trouble, not a direct call from the normal shell launch path to SamSs. They could indirectly matter if a broker, service or application operation requires authentication; correlate PID, timing and a failing security/service API before assigning causality. Neither message proves or rules out the handoff failure.

Static source inspection only; no build, VM, installer run, or probe was performed. The checked source describes this checkout and must be matched to the deployed guest binaries before treating its branches as runtime fact.

## Measured result, 2026-11-05 (traced run in VM B, system role, fixed rpcrt4)

`WINEDEBUG=err+all,+exec,+process,+loaddll` for the whole elevated tree. Findings:

* No `trace:exec` line appears anywhere in the Edge run, not even `ShellExecuteExA`/`W` entry traces, although a probe built from
  `scripts/shellexec_probe.c` run the same way prints them. So the failing "::ShellExecuteEx" of the updater never reaches Wine's
  shell32. Hypotheses 2 to 7 above (resolution, process creation, elevation, broker) are ruled out for this failure.
* The 32-bit updater process loads shell32 and then fails with `err:winediag:nodrv_CreateWindow Application tried to create a
  window, but no driver could be loaded` right before the log line. The lab starts the elevated prefix with `winex11.drv` and
  `winewayland.drv` disabled (`guest-elev-run.sh`), so no window can be created. The updater's ShellExecute helper creates a hidden
  parent window first and reports 0x80004005 when that fails. Working theory: the Edge handoff failure is a lab artifact, not a
  Wine shell bug. Test: give the elevated prefix a display (headless compositor plus winewayland, or an X server plus winex11) and
  rerun. If the handoff then works, the lab recipe needs a display step; if a product session lacks a display for services, window
  creation on the service desktop needs its own look.
* `runas failed: error 1055` (service database locked) happens when the installed updater services make the machine root slow to
  auto-start; `guest-elev-run.sh` now retries.
* The `WINEDEBUG` line in the machine `system.reg` appears twice after `guest-env-debug.py` (an older line in another place);
  check the file after running it.
