## Assessment procedure

1. Start with current parent policy, control-channel and ECN reviews, the requirements document, and existing retained test reports. Record the exact root/Wine commits, file paths, artifact identity and test scope. Do not use logs from another candidate as proof of `fffa7de` without a demonstrated identical build/source binding. Current known outcome: browser, GPU, network and renderer launches; metadata 21/21; `RESULT_CODE_KILLED` and empty HTTP; none establish that the listed call sites executed or the failure cause.
2. Work in priority order: rows 1–5, 7–10, 12–15, 17, 19–21, 27, then conditional graphics and other rows. For each, trace the relevant Win32 wrapper through its actual `Nt*` information class/syscall into Wine Unix/server object, handle, async and synchronization behavior, including x64 and any relevant WoW64 marshaling. Distinguish real implementation from an exported symbol or a success-only return. Identify precise source file, function, commit and line for each claim, plus exact test/result if one exists; if the path or test is missing say unknown.
3. Give every row one of: **sufficient with evidence** (actual behavior tested for this scoped contract), **implemented but unverified**, **partial/stub**, **absent**, **inactive/deferred** (with reason and condition), or **unknown**. A Wine unit test may support a narrow subclaim; it does not prove Chromium reached the call or that the full page works. For conditional rows state the configuration evidence needed before elevating priority. Identify expected failure, fallback, and observable consequences, and distinguish behavior that causes an abort from one that logs and continues.
4. Reuse existing combined token/SID/registration, process, pipe, section, IO completion, socket and graphics tests and their actual outputs. Compare test cases to the precise semantics, including error code/length, inherited or duplicated process-relative handle ownership, token state after revert, `ProcessHandleTable` format, pipe connected status, completion key/OVERLAPPED/bytes/error, and real TCP data. Look at transitive native and server behavior, not only PE wrappers; include WoW64 only where it can actually affect this Windows x64 target or existing relevant tests.
5. Produce a compact assessment table keyed by requirement row with: role/trigger; precise Wine wrapper → NT/server path; status and evidence link; observed test/candidate binding; missing semantic or reachability fact; smallest existing or real PE functional check; and priority/reason. Explicitly mark runtime-inferred versus directly observed. Source or a 21/21 metadata result does not establish effective sandbox access, channel completion, HTTP response or pixels.
6. End with a ranked backlog of **at most 1–3 actual fix candidates**, only if a concrete mismatch and plausible reachable consumer are demonstrated. For each name exact implementation location, real behavior change, existing focused regression and acceptance criterion (including negative/error behavior and an observable real effect). If evidence does not support a specific fix, report zero candidates and the smallest discriminating next assessment; don't fill a quota with guesses. Parent selects and reviews any implementation, including the separately active diagnosis.

## Non-goals and acceptance

This is code assessment/report first. No VM, browser, Wine/probe execution, build, production modification, test weakening or new instrumentation under this draft without separately approved implementation scope. No fake API success or capabilities, security bypass, replacement token stack, speculative navigation retry, or exhaustive UAC/security conformance work. Optional lookup warnings and UDP ECN errors are not automatic blockers; conditional TCP port tuning is ignored at the cited caller. UDP ECN is a real receive/query/ancillary-data contract if later justified, not an accept-and-ignore success stub.

A useful report gives the parent a short, evidence-ranked decision on real Chromium progress, explicitly preserving unknowns and existing failures. It does not promise successful page rendering from source inspection or substitute a broad test framework for a demonstrated fix.
