# Typelib string marshalling: remaining work

Scope: NDR32 object-interface calls created from type information, on both 32- and 64-bit hosts. This is a static plan; no generated `ndr_types.c/.h`, native run, or build was available. Line references below are relative to `wine/` unless stated otherwise. Native Windows 11 behavior and native MIDL output are the authority; the proposed encodings and flag combinations below are hypotheses, not captured Windows output.

## Current behavior and encoding model

Commit `cbaf0d30` adds the two string types to `type_memsize`, `get_stack_size`, `get_param_info`, and the reference table. `ndr_types.idl:29` supplies `[in, string] wchar_t *` and `char *`; `ndr_typelib.c:78-106` copies their parameter type offsets (5 and 6). The existing direct input path selects `MustSize | MustFree | IsIn | IsSimpleRef` (0x010b) with a string referent. `get_basetype` does not classify these as scalars (`ndr_typelib.c:111`); their memory and stack sizes are pointer-sized (`:183`, `:858-905`). Preserve that behavior and test it first.

An LPWSTR is already a pointer even though its TYPEDESC is a single `VT_LPWSTR`. `VT_PTR -> VT_LPWSTR` adds another level. Today `get_param_pointer_info` falls through to `IsSimpleRef` and replaces the TFS descriptor with the bare string (`:917-993`); thus it describes the characters where the interpreter needs a pointer slot. `write_pointer_tfs` only sets `FC_POINTER_DEREF` for explicit `VT_PTR` and interface types (`:717-789`), and the string reference offset is not automatically a nullable pointer descriptor. `ndr_stubless.c:64-117` shows why `IsSimpleRef` changes the address supplied to the NDR routines. A correct solution must preserve both levels and ownership, not just add flags.

Working hypothesis for conventional object IDL with a required outer `[ref]` and nullable inner `[unique, string]` pointer: outer `FC_RP` with `FC_POINTER_DEREF`, pointing to an `FC_UP`/`FC_SIMPLE_POINTER` descriptor for `FC_C_WSTRING` (or `FC_C_CSTRING`), with appropriate padding; alternatively the OIF parameter can use `IsSimpleRef` with a TFS offset directly to the inner `FC_UP`. These can be equivalent representations, but do not mix their flags or dereference semantics. `FC_POINTER_DEFAULT` is not assumed to be an actual opcode: verify the pointer attributes and exact bytes, offsets, allocation flags and OIF flags using native MIDL for the exact IDL and architecture. Pointer attributes/defaults affect nullability; typelib metadata may not preserve all source IDL attributes. Wine's opcode definitions are in `include/ndrtypes.h:28-45,152-175,275`, and string and pointer interpreters in `dlls/rpcrt4/ndr_marshall.c:825,1849,2450`.

To avoid fragile hand-built offsets, add explicit representative reference parameters to `ndr_types.idl` for the required pointer forms, **before** the final BSTR sentinel used to determine the copied TFS length (`ndr_typelib.c:87-93`), or generate the inner descriptor explicitly. Verify that each captured offset points to the correct layer, that both length-only and write passes agree (`:1360-1388`), and that aliases are resolved while their owning `ITypeInfo` and `TYPEATTR` remain valid. Avoid retaining `&attr->tdescAlias` after `ReleaseTypeAttr`; `get_param_info` and `get_param_pointer_info` currently recurse and release it (`:971-982,1045-1064`). Keep the original outer descriptor and typeinfo, or copy/resolve safely. Do not assume `FC_ALLOCED_ON_STACK`, server allocation size, or a simple-pointer optimization matches Windows without checking. Test x86 and x64 because server allocation sizes are expressed in eight-byte units and ABI layout differs.

## Aliases, records and arrays

* Alias: `VT_USERDEFINED -> TKIND_ALIAS -> VT_LPWSTR` is recursively handled by `get_param_info`, `get_basetype`, and `write_type_tfs` (`ndr_typelib.c:135,833,1045`); the pointer helper also recurses. `type_memsize` instead uses the referenced `TYPEATTR` size and alignment (`:202-212`). `get_stack_size` treats a user-defined type through that size and may calculate `byval` differently from a direct string (`:858-905`), and recursive `tfs_tdesc` lifetime is unsafe as noted above. Resolve aliases consistently for ABI classification and pointer depth, without changing record-by-value rules. Test direct and multi-hop aliases in in/out/in-out forms, including alias outside and inside `VT_PTR`; inspect the actual emitted TYPEDESC first. Alias baseline input may already pass; the pointer-output tests must expose the missing layer.
* Record member: pointer size alone is insufficient. `get_struct_member_fc` does not recognize string VTs (`:251-315`), `type_is_non_iface_pointer` recognizes only `VT_PTR` and aliases (`:378-403`), and member/pointer layouts (`:405-599`) can therefore embed a string referent where a pointer field is needed. Teach classification and complex-struct pointer layout/ref generation about both direct and aliased string pointers, respecting offsets/alignment and nullable referents; do not apply parameter `IsSimpleRef` to a member. Candidate is `FC_BOGUS_STRUCT` with `FC_POINTER` and an `FC_UP` to conformant string; exact native form is unverified. Test a record with scalar fields surrounding LPWSTR and LPSTR, input and output with nonempty and NULL members, and an alias member; compare values and free returned members. First verify native typelib marshalling accepts the declaration; mark unsupported native declarations as separate negative tests, not expected successes.
* Fixed C arrays: `VT_CARRAY` uses `get_array_fc` and `write_array_tfs` (`:342-375,628-665`); a string element needs an array of pointer representations, not an array of character referents. Candidate `FC_BOGUS_ARRAY` with embedded unique string pointers, dimensions and offsets from native MIDL; flags depend on parameter direction and array representation. If native typelib marshalling accepts a fixed array of LPWSTR, test two distinct elements and a NULL element across an apartment proxy, plus output and cleanup if native supports it. If the typelib loses size/correlation for conformant arrays, explicitly reject unsupported shapes rather than invent bounds. `SAFEARRAY(VT_LPWSTR)` is out of scope pending proof of a Windows-supported Automation contract; use `SAFEARRAY(BSTR)` for Automation. Record/array work is independent of the small parameter fix and higher risk.

## Interface and Invoke paths

`get_iface_info` unwraps `TKIND_DISPATCH` through implementation index -1 to the underlying interface (`ndr_typelib.c:1404-1436`); dual **vtable** calls that reach this generator use the same `write_iface_fs`. A pure dispinterface need not have such a vtable counterpart; do not claim it takes the same path. Test a native-accepted dual declaration through a marshalled vtable, and separately test a pure dispinterface through `IDispatch`; if raw string types are rejected by native typelib/compiler or Automation, record that result instead of requiring an impossible success. Existing dual and dispatch proxy patterns are in `oleaut32/tests/tmarshal.c:3664,3776`.

`ITypeInfo::Invoke` is separate from the typelib NDR vtable generator. Wine's `typedescvt_to_variantvt` explicitly returns **DISP_E_BADVARTYPE**, not E_NOTIMPL, for `VT_LPSTR`, `VT_LPWSTR`, and unsupported pointer forms (`oleaut32/typelib.c:7014-7063`); `ITypeInfo_fnInvoke` calls it at `:7244`, before `DispCallFunc` at `:7486`. The nearby E_NOTIMPL cases at `:6994-7006` concern records/unions/other type kinds. Whether native Invoke accepts any representation or rejects these types must be measured; VARIANT/Automation support cannot be inferred from TYPEDESC support. If native succeeds, plan a separate conversion/ownership change and native-matching Invoke test; otherwise assert its native error. Do not promise a failing-before-change success test for a form Windows itself rejects.

## Test and implementation order

Use the existing registered test typelib and apartment hosting/proxy setup (`oleaut32/tests/tmarshal.c:75-152,1788,2952`), adding declarations in its associated IDL, server vtable methods and client assertions like the SAFEARRAY/record patterns (`:1423-1457,2580-2616`). Ensure the object is genuinely proxied, not a direct same-apartment call. On Windows 11 first inspect `FUNCDESC` including directions, aliases and return, then run the tests and capture native MIDL `/Oicf` output for matching IDL on x86 and x64; compare OIF flags, type graph, stack offsets, pointer defaults and allocation flags with Wine's emitted graph. Native rejection or unsupported shape changes the test expectation. The intended pre-fix failing tests are out, in-out, retval, pointer-in, and supported record/array/alias variants; do not assert failure until observed. Include empty/non-ASCII wide, ordinary narrow, null inner pointer and repeated calls, cleanup, and adjacent stack arguments to detect corruption. Run the Wine tests only in the later implementation phase; this planning task runs no builds.

1. **Small:** native/typelib inventory and direct in/const baseline tests, capture NDR graphs; no behavior change.
2. **Small-medium:** out wide and narrow pointer slot and retval; fix descriptor lifetime and flags; tests and task allocator ownership.
3. **Small-medium:** pointer-in and in-out, NULL and replacement semantics; alias variants and ABI classification.
4. **Medium-large:** record pointer layouts, then fixed arrays only where native supports them; test both architectures. Correlation and nested ownership are the main risks.
5. **Separate investigation:** dual/dispinterface and Invoke; implement only native-supported semantics. Estimate excludes unknown compatibility failures and native validation time.
