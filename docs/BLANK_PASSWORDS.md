# Blank passwords: at the logon screen only (design)

Status: design, reviewed 2026-11-25 (points G1 to G5 of the reviewer are in). Nothing of it is coded. Until it lands, netapi32
refuses a blank password (`NERR_PasswordTooShort`, parameter 3, for `NetUserAdd` and `NetUserSetInfo` 1003); KNOWN_BUGS B117.

## What the owner decided

A blank password works at the logon screen (the greeter) and nowhere else, as on Windows XP with `LimitBlankPasswordUse`
(`su`, `sudo`, `runas`, a network logon and an elevation with credentials refuse it).

## Why crypt("") is not the answer

`crypt("")` is a hash, so the account would have a real password, the empty string, in every PAM stack that asks `pam_unix`:
`su`, `sudo` and the rest would take it. A blank password has to be an **empty shadow field**, with the greeter letting the
account in by a rule of its own, and every other stack refusing an empty field (no `nullok`).

## The pieces

1. **Client (netapi32, `wexaccounts.c`).** A blank password is sent as its own marker, an empty hash string in
   `WEXA_CREATE_USER` and `WEXA_SET_PASSWORD`, never `crypt("")`. The wire stays as it is (a string of length 0); the helper
   decides. The interim refusal in `hash_of` goes.
2. **Helper (`wex-accountsd`).** The empty string is accepted only in that form, next to the `$6$salt$86 characters` check
   (anything else non-empty that is not that form is `BAD_ARGUMENT`, as now). A blank is made with AccountsService's
   `SetPasswordMode(2)` (`PASSWORD_MODE_NONE`) **on purpose**: it empties the shadow field (`passwd -d`) and puts the user in the
   group `nopasswdlogin`, which is what Debian's greeter stacks use for a passwordless logon, as XP's welcome screen does for a
   blank account. A real hash is `SetPassword("$6$...")` as now.
   **Invariant, kept by the helper: a user is in `nopasswdlogin` if and only if their shadow field is empty.**
   - After every `SetPassword` with a `$6$` hash the helper reads back the password mode (or the group) and removes the user from
     `nopasswdlogin` if AccountsService did not.
   - At start-up the helper lists the members of `nopasswdlogin`, reports every member whose field is not empty, and repairs it
     (removes the membership), and reports a blank field of an account that is not a member.
   - The helper does the group change through AccountsService where it can, and through its own small, root-run operation only
     if AccountsService cannot (the helper's account split, docs/LOCAL_USERS_DESIGN.md); to be settled in the first lab run.
   - Disabled and blank (S3): `SetLocked` runs `usermod -L -e 1`, which turns an empty field into `!`, and `usermod -U` may
     refuse to unlock it, so re-enabling a disabled blank account may fail. Lab-check it; if it fails, a blank account is disabled
     by expiry alone (`usermod -e 1`; enabling is `-e ""`), never by the lock. The group rule does not bypass an expired account:
     `common-account`'s `pam_unix` account check refuses it, and the lab check shows that the greeter runs it. With the atomic
     create (S3, an optional trailing `u32` `locked` in `WEXA_CREATE_USER`) the helper does create, then NONE mode, then the
     expiry, in one operation, so that a blank account that is to be disabled is never enabled, even briefly.
3. **PAM: the only change is that `common-auth` loses `nullok`.** The greeter stays stock: Debian's `lightdm` stack already has
   `auth sufficient pam_succeed_if.so user ingroup nopasswdlogin`. Check `gdm-password` (GDM is the greeter on some images,
   ARCHITECTURE.md) and add that line only where it is missing. Debian 13 ships `nullok` in `/etc/pam.d/common-auth`, generated by
   `pam-auth-update` from `/usr/share/pam-configs/unix` (`[success=end default=ignore] pam_unix.so nullok try_first_pass`); a
   hand edit is undone by the next `pam-auth-update`. So the installer (`setup-machine-root.sh`, the ISO's postinst):
   - `dpkg-divert --add --rename --divert /usr/share/pam-configs/unix.distrib /usr/share/pam-configs/unix`, installs a copy of
     the profile **without** `nullok` (the `Auth` and the `Auth-Initial` lines), and runs `pam-auth-update --force`. The
     diversion survives package upgrades and fails safe: a changed Debian profile leaves ours in place, never `nullok`. Then every
     stack that includes `common-auth` (`su`, `sudo`, `polkit-1`/`pkexec`, `sshd`, `login`, `runuser`, our elevation services)
     refuses an empty field. `sshd`'s `PermitEmptyPasswords no` is the default and stays.
   - Why not a custom `[success=done auth_err=die] pam_unix nullok` line in the greeter, as the first draft had: it hits every
     local user. `success=done` skips the greeter's `gnome_keyring`/`kwallet` auth lines, so keyrings stop unlocking, and
     `auth_err=die` skips `pam_faillock`'s authfail, so failures at the greeter would not count for the lockout policy.
   - **The screen locker (G5):** find out which locker our session uses and which PAM service it calls. If it is not the
     greeter's service, that service gets the same `pam_succeed_if` group line (and no `nullok`), or a blank user could not unlock
     the screen.
4. **Windows side.** `LogonUser` and `runas` with a blank password fail with `ERROR_ACCOUNT_RESTRICTION` (1327), except for the
   interactive logon of the console. Where our logon path (`logonui`, the consent prompt's credentials) does not exist or does
   not check yet, this is a follow-up item, not part of the first change. A network logon with a blank password (SMB, a Windows
   share served by the host) is refused by the same rule: it never goes through the greeter's service.

## Order of the work

1. S3 first: the atomic create with `locked` (a protocol change: an optional trailing `u32`), with the helper and the tests.
2. The helper: the blank form with NONE mode, the invariant (read back after `SetPassword`, the start-up repair), the expiry for
   a disabled blank account, with unit tests (`test_accountsd.py`).
3. The installer part and the PAM files, with the lab checks below.
4. netapi32: send the marker, drop the refusal; the chain test's blank-password check turns into a creation that succeeds.

## Tests

- Unit (helper): the empty string is a blank; a non-empty string not of the `$6$salt$86` form is refused; a blank create reaches
  `CreateUser`, then NONE mode, then (disabled) the expiry; the following hash reaches `SetPassword`; after it the user is not in
  `nopasswdlogin` (the fake bus models the group); the start-up repair removes a member with a non-empty field.
- Lab, on the real AccountsService and PAM:
  - `grep -rn nullok /etc/pam.d` is empty after `pam-auth-update`, and still empty after reinstalling `libpam-runtime`;
  - `pamtester lightdm <blank user> authenticate` passes; `pamtester common-auth`, `su`, `sudo` and `pkexec` refuse it;
  - a user later given `$6$` is not in `nopasswdlogin` (`id -nG`) and must type a password at the greeter;
  - a disabled blank user is refused at the greeter (the account check), and re-enabling works (the `-U` question above);
  - the keyring still unlocks with a typed password at the greeter, and a failure at the greeter counts for `pam_faillock`.
- Chain (`s0_accounts_chain`): a blank create through netapi32 as an elevated administrator; the fake log shows the blank form
  and NONE mode, never a hash of an empty string.
