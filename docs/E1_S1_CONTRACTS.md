# E1-S1: standard-user contracts

Design contract for the disabled E1-S implementation, 2026-11-06. Read with [E1-S](E1_S_STANDARD_USERS.md), especially sections 2–6 and 8–9, and [E1 decisions](E1_DECISIONS.md). This document defines interfaces for later packages, not permission to enable them. H2's [analysis](E1_H2_CALLER_BINDING.md) predates H2a/b/c; its descriptions of zero AuthenticationId and absent opener retention are historical. E1-S3's consumed-message provenance is now implemented; see the current E1 decisions status for its validation. [S5 broker logical records and probes](E1_S5_BROKER_RECORDS.md) are implemented only behind the test define, statically reviewed without build or runtime validation. The full authenticated endpoint/wire/token/profile contracts remain unimplemented.

## Encoding and negotiation

These are logical wire records, not C structure layouts. All integers are unsigned little-endian, of the stated width, with no alignment or padding. `id128`, `nonce` and digests are uninterpreted byte arrays of 16, 32 and 32 bytes respectively. A `blob` is a u32 byte length followed by exactly that many bytes; its limit is stated below. A Windows string is a blob of exact UTF-16LE code units without a terminator, embedded NUL forbidden; do not normalize or case-fold command lines. A SID is a blob containing the validated binary Windows SID (8–68 bytes). A key is a nonzero 16-byte opaque machine-map account-incarnation identifier; it is not a UID, username or SID. S4 owns allocation, persistence, uniqueness, deletion/recreation and protected mapping of this key. An account rename preserves the key; recreation gets a new key. Unknown or ambiguous keys deny.

Every record starts with `kind:u16, version:u16, length:u32, required_caps:u64`; `length` includes this 16-byte header. Version is exactly 1 for this contract; kind values 1–7 correspond in order to the seven records below. Version 1 has no optional trailing fields: wrong kind/version/length, unknown required capability, nonzero reserved value, duplicate field, invalid string/SID, overflow or excess data denies the transaction. Maximum record size is 1 MiB. Receiver checks length before allocation. Different transport framing may encapsulate these bytes, but may not reinterpret them. References and handles mentioned below are connection/server-local objects and are never authorized by their numeric representation alone.

At registration each endpoint exchanges its supported version range and u64 capability mask on its authenticated channel; version 1 requires exact intersection at 1. Bits 0–9 respectively mean `H2_OPENER`, `MESSAGE_PROVENANCE`, `BINDING_V1`, `DIALOG_V1`, `VERIFIER_V1`, `EVIDENCE_V1`, `ACCOUNT_MAP_V1`, `TOKEN_V1`, `PROFILE_V1`, `COMMIT_GUARD_V1`. Every E1-S launch requires all ten across the responsible components; each record's required mask must be a subset of the negotiated mask for that link. Capability advertisement is meaningful only after endpoint authentication and a functional readiness check; a missing endpoint, old server, unsupported version or missing bit visibly denies, never falls back to click consent, a linked token, or an unbound verifier. Existing public `WEXELEVATE_VERSION` 1 is a separate protocol and does not advertise any of these bits.

All generation fields below are nonzero u64 values allocated by their owning authority and never reused within the lifetime of another participant's outstanding record. On restart, authority must invalidate all outstanding state before accepting new work; if uniqueness cannot be guaranteed, fail closed. `root_gen` identifies the protected machine-root configuration and identity, `server_gen` the wineserver instance, `broker_gen` the registered broker instance, `verifier_gen` the native service instance, `map_gen` the account/SID map snapshot, and `policy_gen` the administrator eligibility policy and group snapshot. These are comparisons to current authoritative state, not caller assertions. Time values are u64 nanoseconds from the verifier host's monotonic clock, scoped to its current boot; use a common kernel clock shared by broker-side native transport and verifier, and invalidate on boot/service restart. Reject clock failure, overflow, expiry `now >= expiry`, or disagreement; no persisted monotonic timestamp survives restart.

For a digest, SHA-256 covers ASCII domain tag including its terminating NUL followed by the exact canonical record or field sequence specified here. Integers use the encoding above; blobs include their length. `binding_digest = SHA256("E1S1-BIND\0" || caller-binding record)`. The request digest uses `"E1S1-REQ\0"`, then in order `request_id:u64`, `binding_digest:32`, image identity (volume serial:u64, file index:u64, file size:u64, last-write FILETIME:u64, SHA-256:32), image path, command line and absolute cwd as Windows strings, `env_policy:u32` (1 = fresh managed environment only), `show:u32`, `flags:u32`, and `deadline:u64`. The broker obtains file identity/hash from the held file, freezes these exact bytes, and rejects a nonabsolute/invalid cwd or inherited environment. Any different encoding or changed field produces a different digest. Paths are descriptive; held object and lease checks remain authoritative.

S5 also stores a broker-local `environment_digest = SHA256("E1S1-ENV\0" || env_policy:u32)`. This freezes the managed environment policy, not a future S15 environment block; it does not add a field to the request digest or change any wire record.

## Records

Fields appear in order after the common header. The proposed private operations below are purpose-specific; none is a generic execution or token-grant API.

1. **Caller binding, kind 1.** `server_gen:u64, root_gen:u64, broker_gen:u64, prefix_id:id128, host_uid:u64, host_process_id:id128, opener_id:id128, writer_id:id128, primary_token_id:u64, primary_modified_id:u64, auth_id:u64, session_id:u32, open_impersonated:u8, write_impersonated:u8, reserved:u16, caller_sid:SID, desktop_route:id128`. The server creates nonzero opaque identifiers for retained objects, unique within their generation; it retains actual opener, consumed writer and original primary-token object references. `host_process_id` is an endorsed pinned native process identity, not a PID supplied by a client; `prefix_id` and `desktop_route` are trusted pinned identities, not paths or numerical session alone. Both impersonation flags must be zero, opener and writer must refer to the same process object, and its current primary object and security version must still match. Token and auth LUIDs encode low 32 bits then high 32 bits as a u64; auth_id must be nonzero. H2/S3 now returns retained opener and consumed-writer process/token handles, PID, start time, token/modified IDs and impersonation/current flags, including transceive provenance and security-relevant version updates. It does **not** supply this full record's endorsed native/endpoint identities, generations or server-issued opaque object IDs. These opaque IDs never replace object comparisons; S5 fixtures cannot establish those missing authorities.

2. **Answer, kind 2.** `request_id:u64, attempt:u32, round:u32, message_index:u32, answer_kind:u32, nonce:32, binding_digest:32, request_digest:32, channel_id:id128, payload:blob` (at most 4096 bytes). `answer_kind` 1 is UTF-8 conversation text, 2 is explicit consent/confirmation with empty payload, 3 is cancellation with empty payload. UTF-8 must be well formed, without NUL; prompt styles and echo policy are set by the verifier, never by the answer. The private dialog-to-verifier channel carries kind 1; the broker-owned dialog channel carries kind 2/3. Match exact request, attempt, nonce, channel, expected round/index and sequence; reject duplicates, extra, missing, late or misdirected responses. Do not log payloads, raw prompts or module diagnostics. Bound all challenge counts and bytes; unsupported PAM styles/encoding/order deny. Wipe owned secret buffers on all exits, disable clipboard/history and suppress dumps where supported. This record is an input, never proof of authentication or authorization. Canonicalization to a different displayed account requires a new explicit confirmation bound to the final account before launch.

3. **Evidence, kind 3.** `request_id:u64, request_digest:32, binding_digest:32, nonce:32, attempt:u32, account_key:id128, host_uid:u64, completed:u64, expiry:u64, root_gen:u64, server_gen:u64, broker_gen:u64, verifier_gen:u64, map_gen:u64, policy_gen:u64, method:u32, service:u32`. Method 1 is PAM authenticate plus account management; service 1 is the provisioned fixed `wineexplorer-elevate` service. UID is the verifier's canonical post-PAM account UID, checked against the authoritative map; no supplied username or group flag grants eligibility. Verifier creates this only after both PAM calls succeed and final PAM_USER is resolved; it retains the record and returns a random nonzero `evidence_ref:id128` on the registered broker connection. The reference is a lookup key within that connection, not a portable bearer grant. Redemption atomically removes it, compares every field against broker state and current generations/expiry, and returns the record only once. Cancellation/disconnect/restart destroys it. The broker separately resolves the key, checks eligibility and explicit bound consent. No password, hash, token or reusable approval is in this record.

4. **Token request, kind 4.** `request_id:u64, request_digest:32, binding_digest:32, nonce:32, attempt:u32, account_key:id128, root_gen:u64, server_gen:u64, broker_gen:u64, map_gen:u64, policy_gen:u64, session_id:u32, reserved:u32`. This is accepted only from the registered system-role broker on its authenticated server connection, after it has redeemed evidence and installed a server-owned, request-scoped consumed record containing the same fields and retained caller objects. The operation atomically consumes that server record; replay or any mismatch denies even if token creation subsequently fails. The server independently resolves trusted account data and current generations; no caller-supplied SID, groups, privileges, token handle or boolean authentication assertion is accepted. There is no retry of a consumed request.

5. **Token response, kind 5.** `request_id:u64, server_gen:u64, status:u32, reserved:u32, token_ref:id128, account_key:id128, user_sid:SID, auth_id:u64, token_id:u64, session_id:u32, token_type:u32, elevation:u32, integrity:u32`. On success `token_ref` identifies a non-inheritable broker-only server token handle; its actual handle transfer is authenticated and scoped to that broker connection, not a client-resolvable ID. The broker independently queries the actual token, including groups, privileges, owner/default DACL and logon SID; response fields are consistency checks, not a substitute. Require Primary/Full/High, mapped SID, new nonzero server-allocated AuthenticationId distinct from caller's, a logon SID derived from that LUID, and bound session. On failure status is nonzero, all fixed result fields are zero and SID blob is empty; no handle is transferred. Server generation scopes LUIDs and IDs. Neither this token nor profile-management handles go to the caller.

6. **Profile lease, kind 6.** `lease_id:id128, request_id:u64, server_gen:u64, prefix_id:id128, account_key:id128, user_sid:SID, map_gen:u64, profile_generation:u64, state:u32`. State 1 is acquired for setup, 2 transferred to the server's committed process/descendant tracking, 3 released. Server manager allocates unique lease IDs and owns the actual references, lock, HKU load and durable-save state; record bytes are diagnostic, not a transferable capability. A lease names the exact prefix/SID/incarnation and matching mapping, not the per-logon LUID. Manager serializes provisioning/load/unload, rejects conflicts and unknown existing hives, tracks descendants and open keys, and retains a loaded hive when safe unload is impossible. Failed setup releases only its own reference after child termination/reaping. Restart invalidates old lease IDs and requires locked, checked recovery; failed save is never reported durable.

7. **Registration binding, kind 7.** `role:u32, reserved:u32, endpoint_id:id128, root_gen:u64, server_gen:u64, broker_gen:u64, verifier_gen:u64, host_process_id:id128, channel_id:id128, session_id:u32, reserved2:u32`. Roles 1, 2 and 3 are broker, verifier and one-request dialog. All identifiers are nonzero and issued/verified by the authority that retains the corresponding process/connection object. Fields are evidence of a successful registration only on the authenticated channel; a serialized record submitted by itself proves nothing.

## Endpoint establishment and ownership

The protected machine-root launcher and wineserver already enforce the system role. Extend their trusted channel so that the server endorses only the actual launched broker process object, its SYSTEM primary token with enabled SeTcbPrivilege, root/server/broker generations, pinned host process and a fresh private connection. The native verifier is a supervised root-owned service installed and configured through protected root-owned paths; the broker cannot nominate an arbitrary verifier executable or bus name. The verifier authenticates the server/launcher endpoint and generation using kernel peer credentials plus protected provisioning, then verifies the server's one-connection broker endorsement and pins the system-bus unique owner and host process identity. A same-UID bus peer, SYSTEM SID alone, caller-supplied PID/path or a secret in the prefix is insufficient. Losing ownership, process identity or any generation revokes registration and outstanding transactions. The exact kernel-supported process pin and endorsement implementation must be validated on supported hosts; inability to establish it denies.

Only that broker creates the protected credential child for one request and registers the actual child process object, session/desktop and private channel with the server. The verifier accepts the dialog channel only when this registration is bound to the broker transaction; it must verify the actual channel endpoint, not a claimed parent PID. The broker passes only that channel to that child; no inherited caller handles. Dialog death or channel replacement cancels. The verifier may register only through protected service startup, not through an ordinary Wine client. It verifies identity and returns evidence; it never approves or launches a program. wexhost transports metadata and private FD/channel, but its existing polkit helper is not that verifier. Native passwords travel only between dialog and verifier, never through broker records or public bus metadata.

## Ordered same-UID launch checks

The broker performs these in order, with the indicated rechecks; any unavailable capability or failed check cancels visibly and rolls back. Concurrent cancel, stop, disconnect, death, timeout or integrity break wins over success at each transition.

1. Authenticate broker/server/root and verifier registrations and all required capabilities. Verify the real pipe opener and consumed writer, no impersonation, checked reversion, current retained primary token/version, live caller, nonzero logon and matching pipe/primary session. Accept only the supported ordinary standard token without linked admin token; preserve the separate filtered-admin path and its same-logon linked-token rule.
2. Parse and freeze image object, supported local filesystem, identity/hash/lease, exact command, absolute cwd, flags, environment policy, route and binding. Reject inherited environment and known requirements for administrator host UID/groups/home/keyring, PAM host session or cross-UID admission. Allocate collision-checked request ID, random nonce and one absolute deadline including queue time; fail on RNG failure.
3. Serialize credential and click prompts per bound session. Start the specific protected child on the validated desktop; failure to establish, switch or route presentation denies. Default secure desktop; explicitly configured ordinary desktop is labelled insecure. Display broker-derived requester/image/publisher and Wine-only storage/host-access limits.
4. Bind each account attempt, challenge, answer and confirmation to frozen request, caller digest, channel, nonce and generation. Run the fixed PAM service's bounded conversation, `pam_authenticate` with null-token rejection and `pam_acct_mgmt`; no host credential/session installation. Resolve final PAM_USER to the protected account key and fresh eligibility snapshot, including primary and supplementary group membership. Deny unsupported or ambiguous accounts, stale policy/map, failed account checks, unexpected redirection without bound confirmation, or missing explicit consent.
5. Revalidate caller objects/version/session, request/image lease, desktop, deadline, endpoint ownership, generations and current eligible account. Atomically let cancellation win, consume broker request and redeem connection-owned evidence once. A mismatch or failed redemption ends this request; no reused evidence or silent retry.
6. Install the consumed record in wineserver and request its one constrained token. Validate actual token SID, shape, fresh logon/logon SID, groups, privileges, DACL and caller's session. Acquire a server-managed profile lease for the exact prefix/SID/incarnation; validate anchored paths, ownership, ACLs, hive identity and HKU load. Fail closed on conflicting state, unsafe files, unconfirmed save/recovery or absent hive.
7. Build Alice's fresh Windows identity/profile environment only after the lease; keep sanitized Bob Unix HOME/USER/LOGNAME and validated session resources. Check absolute cwd against both Alice Wine access and Bob host access. Keep Bob UID and ordinary groups, prefix, wineserver and session, with only existing approved wexsys role access. No host-root or Alice-UID fallback. Native Bob can access Bob-owned prefix data and raw Unix I/O remains Bob's; not all future target syscalls can be predicted.
8. Create suspended in the same server with explicit token, profile, normal desktop and restrictive process/thread descriptors; no inherited caller handles. Verify installed child token and process session; duplicate only the requested non-inheritable wait/limited-query handle to caller. Recheck held image/hash/lease and all caller, account, endpoint, generation, deadline and cancellation gates immediately before guarded resume. Arm lease/guard and transfer profile ownership before commit. On precommit failure terminate/reap child, close remote handle in caller, revoke uncommitted state and release only this lease. After commit never retry; a lost reply reported as failure requires termination first. Target-only lease-break and service-stop limits remain as stated in E1 decisions.

## Transition authority

Only the broker owns the request state machine, under one lock/serialized compare-and-transition with cancellation precedence. The verifier owns only its private PAM and evidence state; the server owns token and profile objects. Neither independently commits a launch.

| Transition | Sole writer and required event |
| --- | --- |
| absent → queued | Broker after binding, freeze, quota admission and deadline creation. |
| queued → prompting | Broker after acquiring the per-session prompt slot and verifying its child/channel and desktop. |
| prompting → authenticating | Broker after bound account selection and starting the verifier transaction. Verifier controls its own worker, not this state. |
| authenticating → identity-ready | Broker after receiving a verifier-owned evidence reference and bound dialog consent; this does not authorize launch. |
| identity-ready → consumed | Broker atomically closes the pending request to cancellation/replay and redeems evidence; any redemption failure goes to cancelled. Verifier atomically consumes its evidence; server separately consumes the installed record at issuance. |
| consumed → launch-prepared | Broker after token/profile validation, suspended child, limited handle and guarded lease setup; server retains profile references. |
| launch-prepared → committed | Broker after final gates and successful guarded resume; server manager owns transferred profile references. |
| any uncommitted state → cancelled | Broker on cancel or failure; supervisor executes and confirms cleanup even if broker dies. Verifier/server independently invalidate their subordinate state on disconnect/restart. Cancellation is idempotent; late success cannot reverse it. |

Commit and cancellation must be serialized so neither can win after the other. A committed request is never changed to cancelled to imply its effects were undone; lost-reply termination and reporting follow the existing decision. The supervisor's crash-proof implementation and exact interprocess synchronization remain unverified S19 work.

## Owner decisions and verification gates

No further owner decision is required to implement disabled lab packages under the proposed defaults. Before production, E1-S section 9 requires decisions on the local-account/group/typed-entry subset, supported distro/PAM/filesystem/display matrix, PAM/MFA and lockout policy plus audit retention/failure policy, and whether existing target-only/service-stop protection limits suffice. Three attempts and 120 seconds are proposed limits for lab work, not established production policy. Wine-only identity, broker authority and the lost-reply termination rule are already decided.

All new record formats, endpoint pinning, per-message provenance, generation/clock behavior, multi-account map and SID collision handling, PAM conversation and secrets, explicit token/session/logon SID, profile ACL/hive persistence and recovery, same-server launch, presentation and supervisor races require implementation and the corresponding E1-S section 8 tests. Do not infer production readiness from this document, a compile, a stub or a successful PAM transaction.
