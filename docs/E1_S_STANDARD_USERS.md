# E1-S: standard-user administrator credentials

Design proposal, 2026-11-06. This is a work order for the next elevation track, not a claim that credential elevation works today. Read together with [E1 decisions](E1_DECISIONS.md), [the architecture discussion](E1_ARCHITECTURE_DISCUSSION.md), [the system-role work order](ELEVATION_SYSTEM_ROLE_WORKORDER.md), [caller binding](E1_H2_CALLER_BINDING.md), and `src/programs/wexelevate/main.c`.

## 1. Contract and inspected baseline

The owner has decided that `wexelevate` keeps authorization, request freezing and token use. A standard user must see a consent dialog asking for an administrator's credentials. PAM or polkit may supply an authenticated administrator identity; neither may approve the Wine launch. Every failure denies visibly. Passwords and other authentication answers must never enter logs. Presentation is best effort within the documented Wine/X11/Wayland limits; a detected presentation failure still denies.

The recommended authentication backend is a dedicated native PAM verifier reached through wexhost over the system D-Bus, with a private conversation channel to the broker-created credential dialog. Authentication evidence is connection-bound and single-use. The broker checks eligibility and the frozen request, then asks trusted wineserver code to issue that administrator account's full primary token with a new authentication ID in the caller's interactive session. It does not elevate the standard user's token.

There is a separate, substantial execution problem: Wine identity, host UID, profile and registry identity must agree when the administrator differs from the interactive user. Recommend actual execution under the administrator's host UID, with a narrowly constrained root launch mechanism and new server support. The existing same-UID, setgid-`wexsys` arrangement cannot provide this by itself. This recommendation needs the owner decision in section 9; until the required support passes acceptance, different-account launches deny as unsupported. A successful PAM test is not completion of E1-S.

Source inspection for this document establishes the following baseline:

* `identify_caller()` accepts only `TokenElevationTypeLimited`. `check_binding()` uses `NtQueryWexPipeCallerBinding`, retained opener process/primary-token object comparisons, no impersonation at open, an unchanged primary token, nonzero matching AuthenticationId and equal pipe/primary token session. Standard and already elevated callers are unsupported.
* `launch()` obtains the caller's linked Primary/Full token and requires the same AuthenticationId as the caller. It builds a default environment with `CreateEnvironmentBlock`, but also accepts `WEXELEVATE_ENV_INHERIT`. It supplies the caller as parent, creates suspended, duplicates only wait/limited-query rights, arms the lease and resumes. None of this selects another administrator account.
* `approve_consent()` trusts the exit status of its own click-consent child; it has no authenticated-account result. Production request IDs are not currently passed through a credential protocol. The current table uses a random 64-bit correlation ID and request-object identity; a public ID is not an approval capability.
* The current waits and cleanup are useful foundations, not proof of the stronger E1-S lifecycle below. In particular, `RevertToSelf()` is unchecked, binding is not fully revalidated at commit, per-message writer provenance remains unfinished, multiple prompts can coexist, and crash/stop protection of committed targets has documented limits. `ensure_dir_chain()` is best effort and does not establish safe cross-account profile provisioning.
* The system-role work order reports a protected `root:wexsys` machine root, launcher/server role checks, and administrator membership read at session start from `getgrouplist`, default group `sudo`, with a protected `admin_group=` override. These are reported historical implementation/test results, not rerun here. That document also records the unfinished authoritative Administrators member list.
* Additional inspection of `src/dlls/wexhost/unixlib.c`, its polkit-agent section, finds existing agent registration, cookie handling and `polkit-agent-helper-1` plumbing. `run_helper()` supplies one password answer and returns a Boolean; it is not an E1-S request-bound identity verifier. This is a reuse candidate, not evidence of a secure E1-S backend. The LightDM greeter authentication path is a different login transaction and must not be borrowed as elevation evidence.

The older caller-binding analysis describes pre-H2 code. Its proposed stronger checks remain requirements where relevant, but E1_DECISIONS.md and the inspected broker record the H2a/b/c improvements already landed. Do not reintroduce zero authentication IDs or remove opener binding to admit standard users.

No builds, guest tests, real authentication, or installed-system acceptance were performed for this document. External API facts were checked against the upstream references linked below; distro PAM stacks, installed polkit versions, host-session routing and cross-account Wine behavior remain unverified.

## 2. Eligible administrators and the machine's account view

### Mapping and configuration

Keep three authorities distinct: an eligible administrator maps to Wine `BUILTIN\Administrators` (`S-1-5-32-544`); `wexsys` grants protected machine-tier host access to approved processes; Linux UID 0 is host root. Membership in one is not evidence of membership in the others.

Use one root-controlled administrator-group mapping for ordinary logon token creation, E1-S, and the Wine local Administrators view. Retain `sudo` as the compatibility default. On a machine using `wheel` or `admin`, provisioning explicitly selects that group through protected `admin_group=` configuration. A later version may support an explicit list whose union maps to Administrators, but must version that change. Do not silently union every group named sudo/wheel/admin or let a request/environment variable select a group. `adm`, `staff`, `users`, `wexsys`, and the machine-root ownership group are not administrator aliases. This mapping is a Wine policy choice, not an interpretation of sudoers command permissions or polkit's administrator rules.

Resolve each selected account through the host account database and include primary as well as supplementary groups (`getgrouplist` or the accepted NSS equivalent). A `gr_mem` walk alone misses primary-group members. A valid credential result for an account outside the configured group is insufficient. A disabled, expired or otherwise disallowed account also fails. Recommend initially supporting provisioned local accounts only, excluding UID 0, service accounts and ambiguous UID aliases; network/directory accounts require a separate acceptance profile. Root is not implicitly a Wine administrator. Exact local-account classification and NSS provider support are provisioning work, not inferred from a username or UID threshold.

The authenticated account needs a stable host account key, canonical name, UID, primary GID and an authoritative Wine SID mapping. Reuse the tree's established UID/account-to-SID convention after verifying it; do not invent a different SID algorithm in the broker, use a display name as a key, or accept a caller-supplied SID. Store an account incarnation/version so deletion and recreation with a reused UID cannot reuse an old profile or pending result. This storage and migration do not exist merely because NSS returns a UID. Account identity ambiguity, lookup error, missing groups or unsupported provider denies.

### How the machine root learns identities

Provisioning installs the group rule and identity-map schema in root-owned configuration with protected ancestors, checked on open descriptors. The native identity provider reads NSS and publishes a generation-tagged snapshot over an authenticated service channel. The protected machine root's broker/server consumes that snapshot; an ordinary user's prefix, HKCU, AccountsService display data, environment or `NetLocalGroupGetMembers` client result is never the authority. The machine root need not hold password hashes or a credential cache.

Prefer typed administrator-name entry rather than exposing the complete administrator list in the credential prompt. The provider may resolve one submitted name privately. An optional account chooser must use the same authoritative snapshot and is a separate disclosure decision. Wine's Administrators membership APIs should eventually read the server's authoritative snapshot, not independently enumerate Unix groups. Unknown or incomplete enumeration must not accidentally mean "every user" or "no check needed".

Preserve the existing rule that changes to an established interactive user's group membership affect that user's ordinary token at next logon. E1-S creates a fresh administrator logon: obtain a fresh eligibility/account snapshot after authentication, bind its generation to the request, and check again before commit. A removed administrator cannot use an old interactive-session snapshot for a new credential launch. If policy/account identity changes while a prompt is pending, cancel and require a new request. Existing committed tokens retain their logon snapshot; immediate revocation of running processes is outside this proposal. Freshness across remote NSS caches is unverified and one reason to start with local accounts.

## 3. Collecting and verifying credentials inside Wine

### Alternatives

| Approach | Credentials and verification | Fit for broker-owned authorization |
| --- | --- | --- |
| Native PAM verifier via wexhost D-Bus | The protected Wine dialog renders a bounded native PAM conversation. A dedicated native worker runs one fixed PAM service and returns canonical authenticated account evidence. | Recommended. Gives an explicit account result and controllable request lifetime without importing an elevation policy authority. Requires privileged host authentication support and careful secret transport. |
| A polkit authentication agent | A registered agent presents the identity challenge and uses polkit's helper/backend. The authority normally returns an authorization result for a subject/action. | Possible later only with a verified, privileged, request-bound identity-evidence adapter. An ordinary agent callback or CheckAuthorization Boolean is insufficient. Adds authority/rule/cache/session semantics that do not match our ownership contract directly. |
| A custom root helper | A small root-owned helper can run PAM and, separately, perform constrained host identity switching. Direct shadow-password checking would instead create a new credential stack. | Root privilege is an implementation requirement for some backends and for cross-UID launch, not a replacement for PAM or the broker. Use a supervised narrow service; avoid a general-purpose setuid "run this command" interface. |

These are not completely exclusive choices: the recommended PAM verifier may need a root worker, and actual cross-UID execution needs a privileged host mechanism regardless of the prompt backend. Do not run all of wexhost, the Wine UI or the PE target as Linux root. The current broker has `wexsys`, not `CAP_SETUID` or authority to verify arbitrary users' passwords. An unprivileged `pam_unix` call must not be assumed able to authenticate a different account on every distro.

### Recommended PAM flow

The broker starts its protected SYSTEM consent child in the caller's bound session, normally on `WinSta0\Winlogon`, after freezing the image and request. The dialog says "Enter an administrator's credentials to run this program", identifies the requesting account, and shows the broker-derived image path, SHA-256, publisher status, command details and session. It distinguishes the selected run-as account from the requester. Submit means authenticate and consent to this exact request; Cancel is always available. If PAM canonicalization changes the displayed account, update the account and require explicit confirmation before launch.

The Wine UI must never run PAM modules in-process. Add a narrow wexhost client interface to a protected native service on the system bus. D-Bus carries request metadata and establishes the transaction; a dedicated private channel, preferably passed as a Unix FD, carries conversation responses. No password argument, environment variable, registry value, temporary file, broadcast signal or normal D-Bus property is allowed. The broker receives identity evidence, not passwords. Only its credential child and the native verifier handle secret input. An FD channel reduces accidental bus trace exposure; it does not protect against host root or a compromised trusted endpoint.

Each native worker uses a fixed root-owned PAM service, provisionally `wineexplorer-elevate`, with root-owned modules/configuration. The service name and module paths cannot come from the client. The helper sets request-origin metadata from its authenticated registration, starts a new PAM transaction, calls `pam_authenticate` with null-token rejection, then `pam_acct_mgmt`; only full success of both can produce evidence. PAM authentication identifies the account, while account management checks account restrictions. Those checks may deny authentication use; they never grant the Wine execution operation. See upstream [pam_authenticate](https://github.com/linux-pam/linux-pam/blob/master/doc/man/pam_authenticate.3.xml) and [pam_acct_mgmt](https://github.com/linux-pam/linux-pam/blob/master/doc/man/pam_acct_mgmt.3.xml).

After success, obtain the final `PAM_USER`, resolve it again to the canonical account key/UID, and compare it with the selected identity and policy snapshot. Copy needed identity data before ending the PAM transaction. A typed username is not the result. A redirect to an unexpected account denies or requires a new bound confirmation, never silently changes the target. Expired passwords requiring a change, unknown account, locked account, unavailable backend, unsupported challenges and any non-success result deny. Password changes and account recovery are separate flows. Do not call `pam_setcred` or `pam_open_session` in the long-lived broker as a shortcut to target execution; required host-logon/session setup belongs in the scoped target launch worker. The final-user and item-lifetime rules follow upstream [pam_get_item](https://github.com/linux-pam/linux-pam/blob/master/doc/man/pam_get_item.3.xml).

Support bounded multi-message/multi-round conversations. Give every challenge a transaction ID, attempt ID, round and message index; mask `PAM_PROMPT_ECHO_OFF`, render supported echo-on fields deliberately, and display informational/error text as escaped plain text under broker-owned headings. Never answer every prompt with one saved password. The existing one-answer polkit helper loop is insufficient. Unexpected styles, oversized messages, extra answers, invalid encoding, impossible ordering or missing responses fail the transaction. PAM conversation uses an application callback and arrays of messages/responses; see upstream [pam_conv](https://github.com/linux-pam/linux-pam/blob/master/doc/man/pam_conv.3.xml). Which MFA modules actually work in the guest is unverified; a module requiring an unsupported interaction denies visibly.

Wipe owned UI, marshaling and worker buffers with a non-elidable clearing primitive on completion, cancellation and error; bound allocations, disable credential copying/clipboard and input history, suppress core dumps, and use locked/non-dumpable memory where supported. Audit the selected PAM modules and logging settings too. Do not claim all toolkit, PAM or swap copies are erased without measurement. Never log passwords, OTPs, conversation responses, raw PAM prompt text, arbitrary module diagnostics, full command lines or environment blocks. Safe audit metadata is specified in section 6.

### Why stock polkit is not the initial backend

The upstream [Authority interface](https://github.com/polkit-org/polkit/blob/master/data/org.freedesktop.PolicyKit1.Authority.xml) defines CheckAuthorization results as authorization flags plus details; it does not define that result as the authenticated administrator's canonical UID. AuthenticationAgentResponse methods convey an identity and cookie to the authority. That direction does not provide our broker with authenticated identity evidence. Rules can also return authorization without a new credential challenge, and retained authorization conflicts with fresh per-request credentials.

If a future adapter uses polkit, require a fresh challenge for this transaction and an authoritative selected-identity result from the privileged verifier, bound as in section 4. Do not trust a UID reported by an ordinary session agent, an agent's SUCCESS line, journal scraping, `pkexec` exit status, or arbitrary details inserted by the caller. A polkit YES can never by itself approve E1-S; NO or errors can only cause failure. The original bound requester/session must be represented intentionally, not the root deputy's own subject. If installed polkit offers no supported identity-evidence route satisfying this contract, that backend remains unsupported. No stock API extension is assumed to exist.

### Presentation limits

Serialize credential and click-consent prompts together per bound session. Keep one absolute deadline including queue time, PAM delay and conversation rounds; retries cannot extend it. Failure to establish/switch the intended desktop or route native challenges into it denies. A host agent opening on an obscured desktop is not successful presentation. Preserve the owner's ordinary-desktop policy option when explicitly configured and label its insecurity; default remains the secure desktop. Credentials increase the cost of the accepted same-user native X11 spoofing/keylogging limitation. Wayland compositor isolation and physical input routing require separate guest evidence. No secure-attention gesture or phishing-proof prompt is claimed.

## 4. Binding authentication to the request and caller

The following interface and state machine are proposed, not existing APIs. Public method names are intentionally left for E1-S1. Prefer connection-owned server state over signed portable bearer grants; no "authenticated=true" field may be supplied by a Wine client.

1. **Bind first.** Retain the H2 pipe opener process and original primary-token objects. Record the caller SID, nonzero AuthenticationId, TokenId/ModifiedId, Wine session, trusted host UID and pinned host process identity, server generation, machine-root identity/generation, broker generation and intended desktop/session route. Close the per-message writer/impersonation gap from E1-H2 before accepting credentials: provenance must refer to the actual message consumed, including transceive. A different writer, changed primary token, failed reversion, unknown server capability or impersonating open/write denies. A standard-user token must have the supported ordinary standard shape and no linked admin token; a filtered restricted token is not evidence of administrator eligibility.
2. **Freeze and challenge.** Allocate the existing random request ID under quotas, collision-check live IDs, and retain immutable image object/identity/hash, exact command line, absolute cwd, environment policy, show state and caller binding. Add a fresh cryptographic authentication nonce of at least 128 bits, component generations and a monotonic expiry. Randomness failure denies. Hash a versioned, length-prefixed encoding of those fields into a request digest; avoid ambiguous string concatenation. Every selected-account change creates a new attempt nonce and invalidates prior evidence.
3. **Authenticate endpoints.** Establish a privileged broker registration with the native service using a trusted server/launcher channel. The system bus's peer UID alone is insufficient: broker and hostile clients currently share a host UID, and the bus cannot see a Wine SYSTEM token. A new wineserver endorsement must bind the actual broker role/process object to a pinned native process identity and private connection. The native service authenticates the protected server/launcher endpoint and its generation using kernel credentials and protected provisioning. The UI is the specific protected child created for this request, with a private one-request channel, not any process claiming a parent PID. Never authenticate these endpoints through a public request ID, a client-sent PID/path, or a reusable secret stored in the user prefix.
4. **Begin native transaction.** wexhost sends only frozen metadata through the registered broker connection. The native service associates its transaction with that connection's unique bus owner, service generation, broker/server generation, request ID, request digest, caller-binding digest, authentication nonce, selected canonical account key and expiry. Pin bus ownership and relevant host processes; a later PID lookup alone is insufficient. The dialog's private response channel is delegated only to its verified child instance. An arbitrary same-UID bus client cannot create, answer, replace or consume this transaction.
5. **Return evidence.** On PAM and account-check success the service retains a single-use record containing the canonical account identity/UID, mapping and eligibility generation, authentication method/service, completion time and the entire binding above. Deliver an opaque reference over the authenticated connection, then let the broker redeem it on that connection. A correlation ID is not the capability. No password/hash/token handle travels back. The broker independently maps the authenticated identity to the configured Wine administrator policy. A helper's group annotation is input, not a grant.
6. **Approve and consume.** The broker requires explicit consent from its bound dialog, valid fresh identity evidence, current eligibility, unchanged frozen request, caller liveness and repeated H2 binding, correct session/desktop, no stop/disconnect/integrity event and no expiry. It atomically changes its request from pending to consumed and redeems the native evidence once. A consumed grant cannot be resurrected on a token/profile failure; a new attempt requires a new request and fresh credentials. Cancellations take precedence even if a successful result is also ready. Native evidence consumption is not the launch commit: every subsequent setup failure still rolls back.
7. **Create, validate and launch.** Issue only a request-scoped admin token/launch capability through trusted server operations (section 5). Recheck policy/account generation and all cancellation/integrity gates immediately before launch commit. Keep the current held-image/hash/lease checks, suspended creation and remote-handle rollback. Bind every new host-launch acknowledgement to the same record and pinned child, not a numeric PID alone.

Broker, service, bus owner or wineserver restart; caller/prompt death; session loss; cancel; image break; malformed response; timeout; and channel disconnect invalidate uncommitted state at both ends. Cancel messages are idempotent. Late success is discarded and cannot become a cached approval. Use explicit states such as queued, prompting, authenticating, identity-ready, consumed, launch-prepared, committed and cancelled; only the broker can move to authorization/launch states. The privileged verifier authenticates a person, never chooses whether this executable may run.

Before commit, terminate/reap any suspended child, revoke native launch admission, close remote handles in the caller's table, close token/profile leases, kill/reap prompt and PAM workers, release image protection, and restore input on failure. A supervisor must own crash cleanup; bounded waits that fail to confirm cleanup escalate visibly and cannot report a clean rollback. Authentication workers can be killed to bound a stuck module, but cancellation/account-lockout side effects need tests.

After commit, never automatically retry because a reply was lost. E1_DECISIONS.md requires termination before telling the client that a started process failed; the current broker instead leaves a committed process alive when reply delivery fails and closes the remote handle. Resolve this inherited mismatch in the lifecycle package. Do not promise that termination reverses effects already performed. Target-only lease-break termination and loss of protection on service stop remain documented E1 limits until stronger containment is implemented.

## 5. Administrator token and different-account execution

### Wine token issuance

Add a narrow private server operation, callable only by the verified system-role broker with enabled SeTcbPrivilege, for a redeemed request's administrator identity. It must not be a general "make SID X admin" operation available to arbitrary SeTcb-bearing applications. The broker owns the decision; wineserver remains the token issuer/enforcer. Keep the standard-user session's ban on arbitrary linked-token creation and `grant_process_admin_token`; do not relax those existing protections globally.

The new token must be a primary, Full, High-integrity administrator token for the authenticated account: its user/owner SID, appropriate primary group, enabled Administrators SID, trusted account-group snapshot, supported administrator privileges and a restrictive default DACL. Allocate a fresh nonzero AuthenticationId for this authenticated administrator logon, distinct from both the standard caller and any other credential transaction; create the corresponding logon SID consistently. Preserve that logon ID across token duplicates and children. A split counterpart, if required by the token contract, belongs to this new account/logon only. It is never the standard user's linked full token or a copy of SYSTEM with the user SID changed. Exact supported group/privilege shape and linked-token behavior require source/native-contract verification.

Assign the token the caller's verified interactive Wine session through a real trusted server operation. Do not rely on the historically ineffective TokenSessionId setter. Session equality is required; caller/admin SID or AuthenticationId equality is deliberately not required in this branch. Keep separate fields and checks for requesting identity and executing identity so the existing same-logon check in `launch()` remains correct for filtered-admin consent. A credential token must match the authenticated admin SID and fresh logon, never the caller's identity. Validate returned class lengths, SIDs, token type, elevation, integrity, groups, privileges, logon and session before use; fail any incomplete result.

Tokens and profile references stay in the broker/server, never in the standard user's handle table. The caller receives only the real target PID/TID and, if requested, a non-inheritable `SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION` handle. Process/thread descriptors must deny the caller injection, VM write, token access and dangerous handle duplication, including when the caller is recorded as parent. Target/admin credentials confer no new rights on the caller process itself.

### Identity and state of the launched process

| Property | Required E1-S result |
| --- | --- |
| Wine user and logon | Authenticated administrator's SID and a new administrator AuthenticationId, not the standard caller's. |
| Session and desktop | Caller's bound interactive session; target on its validated normal desktop after consent ends, not on the credential desktop. |
| Host identity (recommended) | Administrator UID and ordinary account groups, plus approved effective/saved `wexsys` access using the protected launch mechanism; never host UID 0. |
| Prefix and machine state | Protected machine-root loader, drive mapping and HKLM policy. Never consume the standard user's prefix as privileged loader configuration. |
| Profile and HKCU | The authenticated administrator's provisioned Wine profile and `HKU\<administrator SID>` hive, with HKCU resolved from that token. Neither the requester's hive nor SYSTEM's hive. |
| Environment | A fresh administrator default block from trusted machine defaults and that account's supported profile; administrator USERNAME/USERPROFILE/APPDATA/LOCALAPPDATA/TEMP/TMP. Separate, sanitized host loader environment. |
| Parent and handles | Requester attribution may retain the caller as logical parent only if verified safe; it must not inherit caller token, profile, descriptors, host groups or environment. No inherited handles. |

Example: standard account Bob requests an installer and administrator Alice supplies credentials in Bob's session. The target reports Alice's SID and fresh logon ID; its HKCU writes and per-user installs belong to Alice. Its windows appear in Bob's session. Bob remains standard and cannot open the target for injection. The UI must explain "Runs as Alice; per-user settings belong to Alice" before final consent. The operation is not an install into Bob's HKCU. A target that needs to write Bob's private files may fail; the broker must not silently reopen those files as Bob or merge both profiles.

Provision/load the correct profile before creating the environment or allowing target code to run. Support loading an offline administrator hive when Alice is not interactively logged in. Use anchored, no-symlink traversal, explicit ownership/ACLs and safe hive locking; do not create arbitrary directories from environment strings. Profile identity must survive renames, be separated from reused UIDs, and not be overwritten through a requester-controlled link. Reference-count loaded hives across targets and unload/flush only after their last user exits. If the administrator's other server owns an incompatible hive lock, deny visibly until a safe sharing/serialization mechanism exists. Never substitute a disposable profile while claiming it is Alice's persistent profile. Same-user multi-server hive persistence and locking are unverified.

Reject `WEXELEVATE_ENV_INHERIT` for E1-S initially. The existing filtered-admin option does not justify giving another account Bob's PATH, DLL overrides, host socket variables or TEMP. Build the Windows block only after the correct HKCU/profile mapping is established; `CreateEnvironmentBlock(token, FALSE)` must be tested rather than assumed to switch hives correctly. Host HOME/USER/LOGNAME are Alice's; DISPLAY/Wayland routing is a narrow broker-validated session resource, not a copy of all Bob's environment or keyring/session-bus credentials. No password enters either block. Validate absolute cwd against the target's access and mapping; reject inaccessible cwd rather than silently changing it. Arguments, relative DLLs and user-writable input remain code/dependency risks even with a clean environment.

### Host UID and server boundary: required new work

The current system-role model explicitly runs elevated programs under the interactive Unix UID with `wexsys` as effective group. A Wine token with Alice's SID cannot call `setuid(Alice)` or read Alice's host home by itself. Retaining Bob's UID would leave raw-syscall file ownership/access as Bob and would not provide actual cross-user isolation. That could only be a separately approved Wine-only identity mode with explicit limits; it is not the recommended meaning of "runs as Alice".

For actual Alice execution, add a root-owned native launch mechanism separate from the PAM verifier's identity-only interface. It accepts only the broker's consumed, request-bound launch preparation and a trusted server-issued admission reference. It runs a fixed protected Wine loader with frozen parameters, controlled descriptors and environment; no shell, caller-selected helper or generic root command. It sets Alice's UID and account groups while retaining the deliberately scoped effective/saved `wexsys` group and non-dumpable protection. Audit privilege-drop order and the existing launcher rule refusing users already in the machine group; do not simply reuse its same-UID checks unchanged. Host PAM credential/session establishment, if needed, is owned by this scoped worker with matching teardown and must not move the target to a different display session accidentally. Its contract remains mechanical execution of the broker's decision.

Alice's process must remain in the same trusted Wine object/session domain if the caller is to receive a real target handle. Today the work orders describe per-UID servers and peer-UID checks. Do not open the server socket to all users or connect Alice to an unrelated Alice server and fabricate a handle. Add one-use cross-UID child admission, bound to the broker-created target token, server generation, exact child process object/pidfd, host UID and request. The root mechanism passes a prearranged private connection; the server verifies the final dropped child identity, not merely SO_PEERCRED captured from a root parent before the drop. Ordinary cross-UID connections remain denied. Child creation and admission are transactional and protected before any target code runs.

Admission alone is insufficient: the server often opens paths on behalf of clients. A server still running as Bob must not open Alice's profile as Bob or use `wexsys` to bypass account isolation. Inventory those operations and use narrowly scoped per-account native I/O workers or another reviewed identity-aware implementation. Never switch the entire multiclient server's UID around an untrusted request. Registry storage, default object ownership, file descriptor transfer, descendants, job/guard ownership and desktop access all need this execution-identity treatment. Display access should use a minimal session-specific capability/ACL, not copy Alice's secrets into Bob's session or grant Bob access to Alice's unrelated session.

These host-launch, server-admission, I/O and profile mechanisms are proposed requirements, not found implementations or proven small patches. E1-S1 must establish a feasible minimal subset; split further if the I/O inventory is large. Until all operations needed for a target's supported execution are covered, deny that target/backend. This is the hard dependency for different-account support, not optional polish after a successful password dialog.

## 6. Attack surface and failure behavior

| Attack/failure | Required response and residual limit |
| --- | --- |
| Replay, cached credentials or old result | No approval/password cache or retained polkit authorization. Bind nonce, attempt, request digest, caller and all generations; consume once. Replayed, expired, already-consumed or restart-era results deny. IDs are correlation only. |
| Request A answered for B | Private child channel plus native connection-owned evidence, full request/caller digest and monotonically ordered conversation messages. Swap account, image, args, cwd, session, UID, token or response channel and deny. Username plus SUCCESS is never evidence. |
| Pipe handle delegated to another writer | Require consumed-message provenance, not just opener provenance. Preserve no-impersonation policy and current-token version checks through commit. E1-H2's open-to-write gap must close first. |
| Fake credential window/keylogging | Protected child/image/desktop and trusted request display reduce Wine-side spoofing. Escape path/publisher/account/PAM strings and Unicode controls; never let target text supply trusted headings. Native same-user X11 capture/spoofing and an explicitly ordinary desktop remain accepted presentation limits, with greater credential risk. |
| Brute force and lockout abuse | Fixed PAM service with distro-reviewed failure delay/account policy, plus native service-wide quotas by requester UID/session, account key and global concurrency. Bounded attempts and total deadline survive broker restart through service state. New pipe connections cannot reset counters. |
| Account enumeration | Same public message and error for unknown user, wrong password, non-admin, expired/locked account or disallowed identity: "Administrator credentials could not be verified. Nothing was started." Do not forward PAM_USER_UNKNOWN or raw module text. Normalize local response timing where practical; do not claim constant-time NSS/PAM. |
| Backend substitution/deputy attack | Protected service/configuration, authenticated bus owner and privileged registration, native process pinning and server endorsement. Same UID, user-controlled prefix or claimed Wine SYSTEM flag is insufficient. Never authorize the root helper as though it were the requester. |
| Token/profile confusion | Separate requester/admin identity records; server-issued new logon, verified session, admin-specific profile/HKCU and host UID. Wrong SID/logon/session, missing hive, unsafe path or inherited identity denies. |
| Target setup, integrity or lifecycle failure | No fallback to caller's token, click-only consent, weaker authentication, arbitrary root execution or unprotected image. Roll back before commit; preserve explicit committed outcome afterward. |

Suggested starting limits for lab validation are three authentication submissions per request, one active prompt per session, one active verifier transaction per requester, and a 120-second total request deadline. These are proposed defaults, not measured usability or brute-force protection. Count each failed authentication at the native service even if the dialog crashes. Respect PAM_MAXTRIES, delay and account restrictions; never reset host lockout counters to improve the UI. Module-internal retries must also be bounded. Persistent cross-restart throttling/host lockout policy needs distro review. Throttling can itself let a hostile user deny service or lock out an administrator; there is no claim that quotas eliminate that tradeoff. Show a generic retry-later message without revealing whether a named account is locked.

Every rejection returns zero success-shaped pid/tid/handle fields and a visible client error. Infrastructure failures may distinguish timeout, cancellation, unsupported session, unavailable authentication service, request-integrity failure and launch setup failure without identifying account validity. If the caller has vanished, use a bounded trusted session-level report; never open another credential prompt to report the failure. Failure to restore input or confirm process cleanup escalates to the supervisor. Logging is bounded, protected and rate-limited: request/generation, safe requester/session IDs, frozen image hash, stage, outcome and commit status. Successful authenticated account IDs and detailed backend status belong only in privileged audit data if policy permits. Failed candidate names, raw prompts/answers, password lengths, environment and full command lines are excluded. Audit storage failure behavior needs a documented policy; it must never cause an implicit approval.

## 8. QEMU lab test plan and evidence

Use a disposable snapshotted Linux guest, existing protected machine-root/system-role setup and isolated test broker images. No host or personal credentials enter the guest. Create throw-away Bob (standard), Alice and Carol (mapped administrators), and an authenticated non-admin Eve; use synthetic identities or locked disposable system accounts with a purpose-built test PAM module rather than modifying the real login/sudo stack. The test module implements known dummy answers, failure/account states, multiple rounds, cancellation barriers and lockout counters without checking real passwords. ## 9. Owner questions and explicitly unverified work

The ownership, credential-dialog, loud-denial, secret-logging and best-effort decisions above are settled. The remaining owner choices are:

1. **Meaning of a different run-as user.** Approve actual administrator host UID/profile semantics and the constrained root launch/cross-UID server work recommended here, or explicitly choose a more limited Wine-only identity mode retaining the interactive host UID. The latter must disclose raw-syscall ownership/isolation limits and needs its own profile-storage design; it cannot silently be called full cross-user execution.
2. **Supported accounts and mapping.** Retain one configured group (sudo default; wheel/admin explicitly selected) for the first release? Approve local accounts only, no root/service accounts or UID aliases initially, and typed account entry rather than an administrator chooser? Multiple-group union and directory identities remain later options.
3. **Profile scope and session support.** Require the administrator's persistent Wine profile/HKCU as proposed, with visible denial on unsafe concurrent hive use? Which distro, filesystem and X11/Wayland/session configurations must pass before enablement? Alice's per-user installs/settings belong to Alice even in Bob's session.
4. **Authentication operations.** Approve a dedicated root-owned PAM service/native verifier and separate constrained host launch interface; choose supported password/MFA modules and distro lockout policy. Proposed three-attempt/120-second limits need usability and denial-of-service review. Decide whether privileged successful-account audit metadata is retained and what happens if required audit storage fails.
5. **Inherited launch lifecycle.** Confirm how to enforce the existing decision to terminate before reporting a failed committed launch when reply delivery is lost. The current code leaves that target alive. Decide whether E1-S keeps the already documented target-only integrity termination/service-stop protection limits or requires stronger supervisor/tree containment before credential release.

Unverified prerequisites include authoritative account-incarnation/SID mapping and member enumeration; fresh eligibility across NSS; consumed-message caller provenance and full precommit revalidation; privileged native registration; PAM service privileges/configuration, supported conversations, secret-buffer behavior and lockout; trusted new-account token/logon/session issuance; cross-UID loader admission, server-side native I/O and descendant identity; safe profile/HKCU/environment construction and hive sharing; crash cleanup and committed-reply semantics; and physical input isolation on the supported compositor. Upstream API descriptions establish none of these project-specific guarantees. E1-S remains disabled until the selected subset has implementation and lab evidence.
