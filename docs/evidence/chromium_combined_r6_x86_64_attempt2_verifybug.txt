THE EARLIEST CONCRETE BLOCKER (verbatim from execution.json "error")
--------------------------------------------------------------------------------
  AttributeError("'bytes' object has no attribute 'fileno'")

Location: chromium-combined-r6-20261030-trial.py, the deploy SHA-verify step:
    verdict=json.loads(remote(['python3','-B','-c',guest_verify_code(),GUEST_WINE_BUILD],
                              stdin=json.dumps(record['deploy_manifest']).encode(),
                              timeout=240).stdout)

Root cause: the trial's remote() helper forwards its kwargs straight to
subprocess.run(). Here stdin was passed as a raw BYTES object (the JSON manifest
encoded to bytes). subprocess.run/Popen requires stdin to be a file object or fd,
not raw bytes, so it called .fileno() on the bytes and raised AttributeError.

This is a bug in the r6 trial adaptation I wrote for the full-transfer deploy.
The r5 template had NO in-guest SHA-verify step; its only tar calls used
stdin=archive (a file object from .open('rb')), which is correct. The one-line fix
is to feed the manifest via subprocess.run's input=<bytes> parameter (or a temp
file / argv) instead of stdin=<bytes>. Per the coordinator's hard limit this fix
was NOT applied and no second variant was started — reported for their decision.

This blocker is NOT: a disk issue, a deploy-transfer failure, a Wine-build defect,
a consumer/PE contract mismatch, or a guest-resource problem. The transfer itself
completed cleanly (tar exit 0; file count + byte total match the host manifest).
