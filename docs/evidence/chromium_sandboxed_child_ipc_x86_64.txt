  (b) Low integrity level ALONE does not break inherited-handle usability.
  (c) With bInheritHandles=FALSE, wine silently DROPS every handle in the list.

WHY Chromium uses TRUE: r6 helper.stderr.log shows ALL children pass
PROC_THREAD_ATTRIBUTE_HANDLE_LIST (GPU count 7; network count 8 + capabilities;
storage count 8). The GPU child CONNECTED in r6. If Chromium used bInheritHandles=
FALSE, wine would drop the GPU's handles too and it could not connect. Therefore
Chromium uses bInheritHandles=TRUE, so basic inheritance works for every child and
the network/storage failures must have a DIFFERENT cause (token-specific).

SOURCE ANALYSIS (reconciled tree: D:\DeepThought\Worktrees\wine-reconciliation)
================================================================================
A. Handle-list inheritance is GATED on bInheritHandles in TWO places:

   dlls/kernelbase/process.c:679  (parse -- always runs, prints the count antigravity saw)
       case PROC_THREAD_ATTRIBUTE_HANDLE_LIST:
           handle_list = &attrs->attrs[i];
           TRACE("PROC_THREAD_ATTRIBUTE_HANDLE_LIST handle count %Iu.\n", ...);

   dlls/kernelbase/process.c:304  (forward to NtCreateUserProcess -- GATED)
       if ((process_flags & PROCESS_CREATE_FLAGS_INHERIT_HANDLES) && handle_list) {
           attr->Attributes[pos].Attribute = PS_ATTRIBUTE_HANDLE_LIST; ... }

   dlls/ntdll/unix/process.c:739  (server-side apply -- GATED again)
       case PS_ATTRIBUTE_HANDLE_LIST:
           if (process_flags & PROCESS_CREATE_FLAGS_INHERIT_HANDLES)
               handles_attr = &ps_attr->Attributes[i];

   `inherit` is a direct pass-through of bInheritHandles (kernelbase/process.c:471,497,
   730); there is NO override that sets it when a handle list is present.
   [CORRECTION 2026-10-31: Per Microsoft documentation for UpdateProcThreadAttribute
   (PROC_THREAD_ATTRIBUTE_HANDLE_LIST), bInheritHandles MUST be TRUE when passing an
   explicit handle list to CreateProcess / CreateProcessAsUser. Passing bInheritHandles=FALSE
   with PROC_THREAD_ATTRIBUTE_HANDLE_LIST is not a valid Win32 handle-inheritance request,
   and Wine's gate on PROCESS_CREATE_FLAGS_INHERIT_HANDLES is NOT a Wine bug.]

B. Server-side inherited handles KEEP the parent's full access (no token re-check):

   server/handle.c:343 inherit_handle():
       src = get_handle( parent, handle );
       if (!src || !(src->access & RESERVED_INHERIT)) return;
       ...
       dst[index] = *src;              // same value, same access mask, same object
   => An AppContainer/restricted child inherits the pipe with the PARENT's access
      rights. Using an already-inherited handle is not re-vetted against the child's
      token, so a low-IL/AC child can still write to the inherited mojo pipe. This is
      consistent with KEY RESULT #1 (il_low PRESERVED).

C. Restricted-token / integrity ARE fully implemented in the reconciled build
   (unlike system wine's stubs): server/token.c has filter_group/filter_privilege,
   restricted_sids list + is_restricted, set_token_integrity_level handler, and a
   restricted-SID access check (token.c:1408-1473) applied when OPENING objects.

ROOT CAUSE / NARROWEST HYPOTHESIS
================================================================================
RULED OUT by host evidence + source:
  - "mojo handles don't inherit at all"  -> FALSE: they inherit & are usable with
    bInheritHandles=TRUE (Chromium's pattern), even under low IL.
  - "low integrity level alone breaks it" -> FALSE: il_low PRESERVED.
  - "inherited handle loses access in an AC/restricted child" -> unlikely: server
    copies the parent's full access onto inherited handles (no token re-check).

REMAINING (needs guest, cannot be reproduced on host):
  The two failing children are exactly the ones system wine cannot launch:
    network = AppContainer (PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES)
    storage = restricted token + integrity level
  Narrowest hypothesis: under an AppContainer or restricted+IL token, the child
  fails at the ChildThread channel connect NOT because the inherited pipe handle is
  missing/inaccessible, but because a step in the mojo connect path that OPENS or
  re-validates an object (or creates a child-side resource) is DENIED by the
  reconciled build's token access checks (server/token.c restricted-SID / mandatory-
  label logic) where real Windows would allow it. The GPU child (restricted, NO IL,
  no capabilities) succeeds because its connect path does not trip that check.

CONCRETE WINE BUGS / OBSERVATIONS FOUND (reproducible on host, system wine):
  1. [RETRACTED 2026-10-31]: The earlier claim that bInheritHandles=FALSE +
     PROC_THREAD_ATTRIBUTE_HANDLE_LIST is a Wine bug is RETRACTED. Microsoft's
     UpdateProcThreadAttribute documentation explicitly requires bInheritHandles=TRUE
     when using PROC_THREAD_ATTRIBUTE_HANDLE_LIST. Do NOT patch kernelbase/ntdll to
     bypass bInheritHandles.
  2. InitializeProcThreadAttributeList crashes (0xc0000005) if the Size arg is NULL.

SCOPE CLARIFICATION ON listinherit.exe (2026-10-31):
  listinherit.exe (tests/probes/_wex_ipc_listinherit.c) ONLY tests a synchronous
  WriteFile/ReadFile over an anonymous pipe (CreatePipe) using a single inherited
  handle. While it proves that PROC_THREAD_ATTRIBUTE_HANDLE_LIST with bInheritHandles=TRUE
  delivers the handle value across all 6 token modes, it does NOT test or exonerate:
    - Chromium's named duplex overlapped Mojo PlatformChannel (\\.\pipe\mojo.* with
      PIPE_ACCESS_DUPLEX | FILE_FLAG_OVERLAPPED | FILE_FLAG_FIRST_PIPE_INSTANCE and

    - SetThreadToken(initial) on the suspended child followed by TargetServices::LowerToken

    - IOCP association (CreateIoCompletionPort) and overlapped ReadFile/WriteFile

    - In-band DuplicateHandle(..., DUPLICATE_SAME_ACCESS | DUPLICATE_CLOSE_SOURCE)
      handle transfer and child validation via GetHandleInformation.

Side finding - a real wine access-mask behavior (NOT Chromium's path)
---------------------------------------------------------------------
A token whose HANDLE was opened without TOKEN_QUERY cannot be used to launch a process in
wine. Reproduced in isolation with nohandle.exe (NO handle list, NO attribute list):
base opened TOKEN_DUPLICATE|TOKEN_ASSIGN_PRIMARY => CreateProcessAsUserW FAILED err=5;
base opened TOKEN_ALL_ACCESS => OK child-exit=0. Mechanism:
  * server/token.c:2036  filter_token (CreateRestrictedToken) stamps the NEW token handle
    with the SOURCE handle's access mask:
        access = get_handle_access(current->process, req->handle);
        reply->new_handle = alloc_handle_no_access_check(..., access, 0);
    (real Windows does not constrain a freshly created token by how the source handle was
    opened)
  * server/process.c:1280 NtCreateUserProcess requires TOKEN_QUERY|TOKEN_ASSIGN_PRIMARY on
    the launch token via get_token_obj.
  * server/handle.c:473   (entry->access & access) != access => STATUS_ACCESS_DENIED;
    process.c:1280-1284 then close(socket_fd); goto done; with NO log -> silent abort.
WINEDEBUG -all,+process,+token,+handle trace of the failing nohandle/restr case shows the
client (pid 0024) emitting a single NtCreateUserProcess for noop.exe with NO follow-up
"pid/tid/handles" success line, whereas every other launch in the same trace has both lines
- i.e. the server rejected and closed the socket silently.
Corroboration: wine's OWN test asserts this access-denied outcome for a token lacking
TOKEN_QUERY (dlls/kernelbase/tests/security.c:1052-1062, "should fail without TOKEN_QUERY"
=> ERROR_ACCESS_DENIED).
This is a genuine divergence from Windows but does NOT apply to Chromium (which uses
TOKEN_ALL_ACCESS), so it is not the cause of r6's symptom. Reported for awareness; no wine
source modified and nothing committed.
