# E1-H2 caller binding

Static source review, 2026-11-06, for the E1-H2 work package in docs/E1_DECISIONS.md:46-47 and the authorization requirement in docs/E1_ARCHITECTURE_DISCUSSION.md:163 (section 4, step 3). No builds, execution tests, or network access were used. Only project and Wine source was consulted; no proprietary implementation material or proprietary source filenames are used. References below are repository-relative source lines observed during this review, not installed-system evidence. Another agent owns the concurrent edits to launch(), client_thread(), handle_request(), and random_id(); this review does not edit src/programs/wexelevate/main.c. References to those functions describe the inspected snapshot and can move as that work lands.

The conclusion is that a broker-only comparison of SID, AuthenticationId, session, PID, and creation time cannot yet satisfy step 3. Session and process-time queries work in this tree, but AuthenticationId is a zero-valued stub, and the pipe retains no process reference or request-writer provenance. A held OpenProcess handle protects the object acquired after the lookup, not the earlier connection-to-lookup interval. The smallest complete solution needs a small Wine-side binding facility plus real authentication IDs. The conservative E1 policy proposed below rejects explicit thread impersonation rather than trying to prove arbitrary impersonation tokens equivalent.

## (a) What the broker verifies today

In src/programs/wexelevate/main.c:287-290, token_user_sid() is just GetTokenInformation(TokenUser) into a fixed buffer large enough for TOKEN_USER plus SECURITY_MAX_SID_SIZE. identify_caller(), at lines 324-356, first calls GetNamedPipeClientProcessId(req->pipe, &pid) and rejects failure or zero with ERROR_ACCESS_DENIED (330). It calls ImpersonateNamedPipeClient (331), then OpenThreadToken(GetCurrentThread(), TOKEN_QUERY, TRUE, &thread_token) (332). TRUE makes the token-open access check run as the broker; it does not select the client's primary token. An open failure attempts RevertToSelf and returns ERROR_ACCESS_DENIED (334-335). On success it also calls RevertToSelf (337), obtains only TokenUser from the saved impersonation token (338-342), and closes that token (343). Neither RevertToSelf result is checked. Thus even a reversion failure is not presently a mandatory denial.

It records the pipe PID (345), calls OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_DUP_HANDLE | PROCESS_CREATE_PROCESS | SYNCHRONIZE, FALSE, pid) (346-347), and retains the handle in req->caller. It opens that process's primary token with TOKEN_QUERY | TOKEN_DUPLICATE and retains it in req->caller_token (348). It compares its TokenUser SID with the SID read from the pipe impersonation token using EqualSid (349-350). It repeats GetNamedPipeClientProcessId, requires the same number, and requires WaitForSingleObject(req->caller, 0) == WAIT_TIMEOUT (352-353). WAIT_OBJECT_0 and WAIT_FAILED both deny. Finally GetTokenInformation(TokenElevationType) must succeed and return TokenElevationTypeLimited; a query failure returns ERROR_ACCESS_DENIED and a different elevation type returns ERROR_NOT_SUPPORTED (354-356). Earlier failures are also collapsed to ERROR_ACCESS_DENIED, rather than preserving the underlying diagnostic.

These checks establish same user SID, an unchanged reported numeric PID, a live process acquired by that PID, and a primary token labelled Limited. They do not compare TokenStatistics.AuthenticationId, TokenSessionId, process creation time, token restrictions, groups, integrity, or the primary token at connection-open time. They do not establish that a request-writing thread was not impersonating. The retained handles are closed by free_request() at main.c:237-238. Caller death is included in the approval waits at 729 and 764 and checked before launch at 986; those later checks monitor the process actually opened, which can already be the wrong process.

Outside identify_caller, handle_request() checks system_role before identification and parsing (main.c:978-980); token_is_system_with_tcb() inspects the broker's primary SID and enabled SeTcbPrivilege (293-318), and service startup sets system_role at 1141. The listening pipe descriptor grants SYSTEM and administrators full access and authenticated users read/write access (1028-1034); it uses first-instance protection for the initial listener and PIPE_REJECT_REMOTE_CLIENTS. These flags are requested by the broker; this review does not establish remote-client rejection on an installed system. The request header's advisory_pid is explicitly advisory (src/include/wexelevate.h:59-65) and is not used by identify_caller. Supplying somebody else's number in a request is not the PID-reuse attack below.

The shared client gets the service PID using QueryServiceStatusEx, opens the pipe with CreateFileW and SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION, and compares GetNamedPipeServerProcessId with that service PID (src/include/wexelevate.h:100-138). It writes one request message and reads one reply (184-200). This is a useful endpoint check, but it too compares numeric PIDs; it is not an atomic service-generation proof. No stronger endpoint authentication is claimed here. The broker reads the request before calling identify_caller (main.c:1003-1005). Its launch path gets TokenLinkedToken and requires a primary, Full token (858-872), but does not explicitly compare its SID, logon, or session with the identified token.

The API chain matters. In this Wine tree GetNamedPipeClientProcessId is in wine/dlls/kernel32/sync.c:513-519, not kernelbase. It calls NtFsControlFile with FSCTL_PIPE_GET_CONNECTION_ATTRIBUTE and the attribute ClientProcessId. The server returns the saved pipe_end.client_pid, without looking up its current process object (wine/server/named_pipe.c:1207-1235, 1238-1244). create_pipe_client records current->process's Wine PID and retains the opening thread's token if present, otherwise the process token, only while elevation_enforced() is true (1404-1419). Linking copies the PID to the server end (1469-1476). pipe_end has numeric peer PIDs and a retained token, but no retained peer process (54-69). Destruction releases the token (429-448). These are Wine PIDs, not host PIDs.

ImpersonateNamedPipeClient in wine/dlls/kernelbase/security.c:775-780 issues FSCTL_PIPE_IMPERSONATE. NtFsControlFile forwards that operation to the server (wine/dlls/ntdll/unix/file.c:6575-6578); the connection-attribute operation follows its default server route (6633-6635), through server_ioctl_file's ioctl request (5632-5670). The stale ntdll diagnostic about impersonating self is not the enforced server behavior. Under enforcement the server duplicates the connected client's saved opening token into the broker thread (wine/server/named_pipe.c:1314-1331). Without enforcement it instead duplicates the server process's own token (1333-1340). Production binding must require trusted enforcement and must not fall back to that path. The requested client SQOS level is not transmitted to this server implementation; token_impersonation_level() documents and implements that limitation (wine/server/token.c:1200-1214). The client flag alone is not proof of enforced identification-only behavior.

GetTokenInformation forwards to NtQueryInformationToken (wine/dlls/kernelbase/security.c:705-731). TokenUser uses get_token_sid, whose server handler requires TOKEN_QUERY (wine/server/token.c:2232-2268). TokenStatistics uses get_token_info but ntdll fills AuthenticationId.LowPart and HighPart with zero, explicitly marked FIXME (wine/dlls/ntdll/unix/security.c:506-533, especially 516-517). The server token structure has token_id, modified_id, and lineage_id but no authentication ID (wine/server/token.c:119-141); get_token_info and its protocol reply have no authentication ID either (2312-2337; wine/server/protocol.def:3950-3966). The create_token protocol accepts auth_id (3507), and ntdll sends it (wine/dlls/ntdll/unix/security.c:97-98), but server creation does not store it (wine/server/token.c:1753-1755). Two successful TokenStatistics queries returning zero do not prove a shared logon. TokenId identifies an individual token; lineage_id identifies a derivation chain. Neither can simply be renamed AuthenticationId. The logon group SID is also a fixed placeholder in token_create_admin (884-890), not a substitute logon identity.

TokenSessionId does return server token state (wine/dlls/ntdll/unix/security.c:593-600; wine/server/token.c:2320). Process session and creation time are also available from get_process_info (wine/server/process.c:1512-1535): GetProcessId uses ProcessBasicInformation, GetProcessTimes uses ProcessTimes, and ProcessIdToSessionId opens the PID and queries ProcessSessionInformation (wine/dlls/kernelbase/process.c:1002-1009, 1053-1069, 1239-1253; wine/dlls/ntdll/unix/process.c:1129-1139, 1256-1263, 1422-1435). The creation value is process->start_time, assigned at process initialization (wine/server/process.c:1464); it is not a host /proc birth time or a guaranteed unique generation counter. The default Wine session is 1 (wine/server/process.h:162). Setting TokenSessionId currently reports success without changing it (wine/dlls/ntdll/unix/security.c:764-777). GetNamedPipeClientSessionId is a stub that reports the querying process's PEB session (wine/dlls/kernel32/sync.c:537-543); do not use it for peer authentication.

## (b) Remaining gaps and concrete scenarios

PID reuse before the first process handle: first, limited administrator process A opens the broker pipe and passes a duplicate client handle to cooperating same-user process B, or B inherits it. Second, A supplies a complete request and exits while the broker is paused before OpenProcess; B keeps the connection alive. All other references to A, including a parent's process handle, must be closed. Third, B creates and reaps enough processes/threads for Wine to recycle A's numeric PID to live process C, whose primary token has A's SID and Limited elevation type. Fourth, the broker's OpenProcess(pid) opens C. The saved pipe token still represents A, the two pipe queries still return A's saved number, and C passes the SID and liveness checks. Consent and any eventual parent/returned-handle attribution now concern C. A correct shared-logon comparison would still pass if A and C belong to the same logon; creation time measured only after opening C would not expose the mistake.

This is reachable in principle by an ordinary, unelevated filtered administrator in the same server: duplicate/inherited handles and own-process churn need no machine administration. It requires a scheduler window and actual ID recycling, not guessing a request PID. Wine frees the ID at process object destruction (wine/server/process.c:738-761), and the allocator deliberately delays reuse until the free pool has at least 256 entries when unused entries are exhausted (430-479). A live process handle already held by the broker prevents subsequent destruction/reuse, but none is held during the vulnerable interval. A bare exit without a surviving client handle normally makes impersonation fail once the connection is gone; that alone is not a successful attack. The described timing and complete attack are unverified at runtime. A standard user's own replacement process has no Limited administrator token in the supported setup and remains unsupported; this is not demonstrated standard-user elevation. Even in the successful attribution scenario, current consent is still required; automatic approval is not implied.

Same SID but different logon/session: first, a process P with a Limited primary token for user U, logon L1/session S1 obtains a usable impersonation token for the same SID U in logon L2 or session S2. Second, its thread installs that token and opens the pipe. Third, the broker reads the pipe token's SID U and P's primary SID U, sees a live P and Limited elevation, and proceeds using P's L1/S1 primary token and its linked full token. The effective connection identity L2/S2 has been silently replaced. Session equality alone misses L1 != L2 in one session; authentication equality alone misses a session reassignment. Both comparisons are necessary.

The comparison omission is verified; this cross-logon scenario is conditional and unverified as an ordinary-user exploit in our current fixtures. It requires possession of the other token with sufficient rights. It must not assume an ordinary user can invent a logon, acquire another user's token, change the broker session, or cross wineserver instances. The test script runs separate Unix users with their own servers (scripts/test_sysrun_server.sh:28-30, 52-58); different users' PIDs are not in one global Wine PID namespace. The checked code defaults to session 1 and has no working TokenSessionId setter. Arbitrary token creation is denied under enforcement without SeCreateTokenPrivilege (wine/server/token.c:1659-1664). A trusted lab fixture must provision distinct same-SID logon/session tokens to test this exact mismatch. Multi-session support cannot be inferred from the existing default session value.

Same-logon impersonation with fewer rights is more directly reachable: first, an ordinary filtered administrator opens its own primary token with TOKEN_QUERY | TOKEN_DUPLICATE. Second, it uses CreateRestrictedToken to add Authenticated Users as a restricting SID, then DuplicateTokenEx to obtain a SecurityImpersonation token and SetThreadToken(NULL, token). That restricting SID still permits read/write connection through the pipe's Authenticated Users ACE; an arbitrary restricting SID might simply fail the pipe access check. Third, while impersonating, it opens the broker pipe and sends a request. Fourth, identify_caller sees the unchanged user SID and the live process's ordinary Limited primary token and approves that identity for consent. The restrictions on the opening thread are lost when the broker chooses the process primary token. Token filtering is implemented with TOKEN_DUPLICATE access (wine/server/token.c:1985-2014), and installing a thread token requires a TOKEN_IMPERSONATE handle (195-215). The pipe captures that effective token at open. This construction uses one's own tokens and is source-reachable by an ordinary filtered administrator; complete runtime reproduction remains unverified. It does not itself demonstrate acquisition of rights unavailable to the surrounding process, which already owns the primary token, but it violates the required security-context binding. Correct AuthenticationId and session equality would still accept it. Comparing TokenId across the primary and pipe impersonation tokens would instead reject legitimate callers too, because pipe impersonation creates a new token object.

There is also an open-to-write distinction. First, P opens the pipe without impersonation. Second, P changes its thread to a same-SID restricted token, or duplicates the pipe handle to another process Q. Third, that thread/process writes the request. The saved PID/token still identify the opener P: the server's pipe_message contains no writer process or token (wine/server/named_pipe.c:46-52), and queue_message/pipe_end_write do not capture them (370-379, 1058-1088). Reverting to self after an impersonated open gives the converse stale context. These operations are ordinary-user reachable for one's own token and cooperating processes; runtime reproduction is unverified. Under an explicitly opener-authorized, transferable connection contract, a delegated write is intentional delegation. It is not proof that the writing thread used P's primary context. For the stricter section 4 step 3 requirement, E1 should deny a different writer or explicit impersonation at either open or request write. Querying the client's threads later cannot recover the historical writer context.

## (c) Smallest complete change and exact call sequence

Broker-only hardening can add SID/session checks, retain the process/token handles through consent, and recheck liveness and creation time. It cannot close the pre-open reuse interval, obtain a real AuthenticationId from this tree, or detect the historical impersonation/writer cases. There is no existing pipe query returning an original peer process handle or its creation time/token provenance. FSCTL_PIPE_QUERY_CLIENT_PROCESS is not the implementation behind GetNamedPipeClientProcessId; the device handler only rejects it (wine/server/named_pipe.c:1497-1499), and the connection-attribute handler recognizes only ClientProcessId and ServerProcessId (1213-1225). There is also no usable generic token-equivalence escape hatch: NtCompareTokens returns STATUS_NOT_IMPLEMENTED (wine/dlls/ntdll/unix/server.c:1950-1953).

For the PID gap alone the smallest server change is to retain the opening struct process at connection creation, on the server connection record, until disconnect/destruction. Since free_ptid occurs only when that object is destroyed, the existing PID query followed by OpenProcess can then acquire only the original object; caller death still denies. Acquire that reference while current->process is the opener, not by looking up the saved PID later. Release it on every failed connection setup, disconnect, server-end destruction and instance reuse, with no stale binding on the next client. Process exit already closes its own handles before final destruction (wine/server/process.c:945-955), but reference-cycle and disconnect cleanup still need tests. Merely adding a process-time field obtained by a later PID lookup would not repair the race.

For the full requirement, make that retained connection record queryable through one small, explicitly project-private Wine request, provisionally named get_pipe_caller_binding. This name denotes a proposal, not an existing Win32 API. The request takes the server pipe handle and returns non-inheritable query/synchronize handles to the retained opener process and query-only original primary token, the opener PID, its process start_time, a server-generation identifier, the captured primary TokenId/ModifiedId/session, and validity/provenance for the one request message just read. Capture the primary token reference and its identity/version at open as well as the process, and remember whether the opener had any thread token. Capture writer process identity, primary-token identity/version and presence of a thread token when each message is submitted, including the transceive route; retain the consumed message's provenance before free_message drops it. Associate the query with the exact completed request read, not the latest queued write. Reject incomplete, mixed, missing, disconnected, or superseded provenance. E1 uses one reader, one complete request message, and one request per connection; no general-purpose multi-reader protocol is needed.

The query must validate that the opener is still live, its primary token object/version still matches the captured one at open, write and query, the writer is that same process, and neither opening nor writing used an explicit thread token. Rejecting even a same-identity thread-token duplicate is a deliberate conservative E1 compatibility restriction, requiring clients to open and send as self; it avoids adding a token-semantic-equivalence engine. Do not apply that restriction to ordinary pipe impersonation globally. The private query can reject the unsupported provenance while other pipe users retain their normal semantics. Access checks must use the server endpoint and ordinary handle allocation checks; this must not become a public shortcut for a limited caller to acquire privileged peer/token rights. Handle-allocation failure must close partial allocations and return no success-shaped handles. These semantics require implementation and review; they are unverified as working code.

ModifiedId is not yet a complete change detector in this tree. Privilege adjustment and disable-all allocate a new value (wine/server/token.c:1130-1169), but token_assign_label and set_token_default_dacl do not (863-876, 2382-2404). For the captured-version contract, update ModifiedId on successful security-relevant in-place token changes, including those setters, and verify the mutation paths used by the supported token classes. Alternatively the private query would need immutable security snapshots and structured comparisons; treating the current ModifiedId as sufficient is incorrect. Rechecking only the final token shape could miss a change followed by restoration between open and write. This small version-tracking repair is part of the proposed stock change, not a verified current guarantee.

Add a real authentication_id LUID to server token state and the get_token_info reply, and return it in TokenStatistics instead of ntdll's zeros. Establish it at a trusted logon root, preserve it across token duplication/filtering, primary-token inheritance and pipe impersonation, and explicitly copy the source identity into the linked full token. create_linked_token currently manufactures a fresh administrator token with the source session but no logon field (wine/server/token.c:2408-2448); allocating a new authentication ID on that path would break the required equality. Honor create_token's supplied auth_id only through its existing privileged creation path. For bounded E1, provision one interactive logon identity per trusted per-user/server-session lifetime, shared by independent root client processes in that lifetime, and separate identities for service logons. Do not allocate a new logon ID for every OpenProcess, pipe connect, duplicate, or independent client invocation. Restart invalidates pending grants; cross-server equality is never proof of identity. Mapping multiple host login sessions into one server is not implemented by these fields and must remain unsupported until a trusted session mapping exists. A server-local authentication ID is meaningful only within the verified server generation. Use a capability/version result from the binding query so an older zero-stub server cannot silently pass equality; unsupported or unknown support denies. No real logon identity may use the stub zero value in this E1 contract.

With that server support, the broker's exact sequence is as follows in prose. After reading the single request, invoke the private binding helper and require its supported version and valid non-impersonating provenance. No existing Win32 call can supply this missing operation; a narrow ntdll helper issuing the private server request, exposed to the broker through the existing project bridge if needed, is required. Then call GetNamedPipeClientProcessId and OpenProcess with the existing main.c access mask and FALSE inheritance. Keep this handle until the request ends. Require GetProcessId(held) to equal the pipe PID and CompareObjectHandles(held, bound_peer) to succeed. CompareObjectHandles is implemented through NtCompareObjects and server pointer equality (wine/dlls/kernelbase/process.c:2015-2017; wine/dlls/ntdll/unix/server.c:1931-1943; wine/server/handle.c:960-974). It is exported by kernelbase (wine/dlls/kernelbase/kernelbase.spec:158); no kernel32 export was found in this tree. Resolve the kernelbase export with GetModuleHandleW and GetProcAddress, checking both results and denying if unavailable, rather than assuming the broker's current import libraries expose it. Toolchain declaration/import availability is unverified. Comparing handle numbers is not object comparison. The private query returning a bound handle also permits using that handle directly with suitable access, but the explicit PID reopen and comparison preserves the current broker flow and detects a broken binding implementation.

Call GetProcessTimes(held, &creation, &exit, &kernel, &user), require success and a valid initialized creation value, and retain the creation FILETIME. Require exact equality to the opener process start_time supplied by the binding result; the server-generation value is a separate field. Require WaitForSingleObject(held, 0) == WAIT_TIMEOUT. Creation time is an additional consistency check; the original object reference and CompareObjectHandles provide the identity proof. Two creation-time reads only from a process first opened by PID cannot prove it was the pipe opener, and equal timestamps are not guaranteed unique process identities.

Call ImpersonateNamedPipeClient, then OpenThreadToken(GetCurrentThread(), TOKEN_QUERY, TRUE, &pipe_token), and always check RevertToSelf before any subsequent privileged work. Keep pipe_token until its queries finish. Call OpenProcessToken(held, TOKEN_QUERY | TOKEN_DUPLICATE, &primary_token), require CompareObjectHandles(primary_token, bound_primary) and compare its TokenStatistics.TokenId/ModifiedId with the captured primary values. On both tokens call GetTokenInformation for TokenUser, TokenStatistics and TokenSessionId. Use EqualSid for the SIDs and compare both halves of AuthenticationId; require primary.AuthenticationId == pipe.AuthenticationId and primary.session == pipe.session. Require TokenType == TokenPrimary for the primary and TokenImpersonation for pipe_token; query TokenImpersonationLevel and reject anonymous identity. Do not demand equal TokenId or ModifiedId between the primary and the newly duplicated impersonation token. The private provenance check supplies the fact that no explicit caller thread token was used.

Obtain the process session using ProcessIdToSessionId(held_pid, &process_session) while the process handle remains held and mapping is reverified, and require it equal the primary-token session. Bind that session to the broker's trusted configured interactive session and desktop route, not a request field. In the current one-session server, a broker-session check can use ProcessIdToSessionId(GetCurrentProcessId(), &broker_session); fail setup if that does not represent the intended interactive session. Do not compare the user's authentication ID to SYSTEM's logon ID. Do not trust GetNamedPipeClientSessionId. The stronger handle-based internal alternative is NtQueryInformationProcess(held, ProcessSessionInformation), which is available here but is not a Win32 call. For host UID/server/machine-root binding, retain the existing trusted server/launcher boundary: sysrun captures peer credentials from SO_PEERCRED (wine/server/process.c:643-652), and sysrun_process_privileged uses peer_uid/peer_gid (wine/server/sysrun.c:163-165). The broker has no Win32 query here proving the peer host UID or a machine-root generation. The private binding query should reject unknown/mismatched peer UID under active sysrun; machine-root and desktop provisioning remain trusted setup requirements, unverified on any installed system in this review.

Require TokenElevationTypeLimited as today. For the first-release supported token shape, query TokenIntegrityLevel, TokenGroups, TokenPrivileges, TokenRestrictedSids, TokenIsRestricted and TokenIsAppContainer with GetTokenInformation and require the expected filtered administrator shape, including medium integrity, deny-only Administrators, no additional restricting SIDs and no app container. The expected privilege shape is the server's token_make_filtered result (wine/server/token.c:1943-1962). Compare structured SID/attribute and privilege sets, not raw variable-buffer bytes or group counts. TokenIsRestricted and TokenIsAppContainer have server-backed queries (wine/dlls/ntdll/unix/security.c:672-693). Avoid treating IsTokenRestricted returning FALSE as a successful unrestricted-token query: it also returns FALSE on query/allocation failure (wine/dlls/kernelbase/security.c:794-823). Additional restrictions or unsupported shapes deny; Full/Default/standard callers return visible ERROR_NOT_SUPPORTED. These checks avoid laundering a restricted primary token through the current linked-token factory as well as a restricted thread token.

Before consent, obtain GetTokenInformation(primary_token, TokenLinkedToken, ...) and query the returned token for TokenType, TokenElevationType, TokenUser, TokenStatistics and TokenSessionId. Require Primary, Full, the same user SID, the same AuthenticationId, and the same session as the frozen caller. Retain that validated token for launch; do not discard it and use a newly fetched, unvalidated counterpart. Revalidate the private binding, held caller liveness, primary token object/TokenId/ModifiedId, SID/logon/session and linked-token identity immediately before launch. Reopen the pipe-reported PID with OpenProcess, compare the new handle with held using CompareObjectHandles, and compare GetProcessTimes creation values; close the temporary handle. Require the repeated GetNamedPipeClientProcessId to match as well. All parent selection, caller-death waits and DuplicateHandle destinations must use held, not a later unverified PID lookup. This is a prelaunch recheck contract for the agent owning main.c, not an edit made here. A later caller death is still handled by launch rollback; these separate calls do not provide an atomic launch transaction.

Every failed query, short or malformed result, missing private capability, unknown identity, mismatch, disconnected pipe, or unsupported session denies before target creation. For variable-size GetTokenInformation calls use a bounded two-call allocation, accepting ERROR_INSUFFICIENT_BUFFER only for sizing, checking the actual second result/length, and validating SID bounds/IsValidSid before EqualSid. Check returned lengths for fixed-size classes too. Preserve GetLastError immediately for an API failure and log the failed stage; use ERROR_ACCESS_DENIED for identity mismatch, ERROR_NOT_SUPPORTED for unsupported first-release identity/capability, and ERROR_CANCELLED for an established caller's death. Never interpret WAIT_FAILED as caller liveness. Zero pid/tid/handle in every rejected reply. Close temporary, primary, pipe, bound-peer, bound-primary and linked-token handles under one explicit cleanup owner, including partial acquisition failures.

A failed RevertToSelf is an exceptional security failure: do not continue the worker, run privileged cleanup in the wrong context, or reuse it. Record the failure through a safe path and force broker/service recovery under the trusted supervisor; pending requests must be denied. The precise recovery mechanism and crash cleanup are unverified implementation work. A pipe reply alone is not loud denial if the client has exited: return a distinct visible error to a live client and require a bounded service/session error report otherwise, with failure stage and safe identity metadata, not raw command lines or environment. That fallback is a requirement, not established current behavior. No denial path may fall back to a direct launch, accept zero authentication IDs, or retry as an unbound caller.

The required stock-Wine work is recorded as proposed, not implemented, in docs/STOCK_CHANGES.md under E1-H2. Reusing get_process_info and TokenSessionId needs no new query. Exposing a true authentication ID does. Closing opener PID reuse needs retention at open, and closing the strict impersonation/write gap needs provenance retained before the request is consumed; neither can be reconstructed after the fact by extra Win32 PID queries.

## (d) Test plan, not executed

Extend scripts/wexelevate_probe.c and scripts/test_sysrun_server.sh around the existing broker helpers (593-618), forged advisory-PID case (893), standard-user cases (902-909), consent orchestration (982-1027), caller-death case (1098-1109), and two-user caller coverage. Keep the test broker, consent hook and any deterministic server barriers isolated from shipping builds; the existing checks at 643-671 and 943-955 demonstrate the intended hook exclusion pattern. Some old script comments describe an earlier shipping broker without consent; use actual assertions and current source, not those comments, as the baseline. Run both 32- and 64-bit clients later in disposable lab fixtures. This document adds no executable test hooks and runs none.

Positive controls must show a normal filtered administrator reaching exactly one consent prompt, Continue starting exactly one target with the expected parent/full-token identity, and Cancel leaving no target. Record caller and target SID, AuthenticationId, token session, process session and creation time. Verify a primary token, its legitimate duplicates, the pipe impersonation copy, a child inheriting the logon and the linked full token share AuthenticationId while distinct token objects have different TokenId values. Test independent root client invocations in the same trusted logon. Provision a second logon with the same SID and another with a distinct session through a trusted fixture and verify authentication/session separation; do not pretend SetTokenInformation(TokenSessionId) creates it today. Assert that an old server or the current zero AuthenticationId implementation is explicitly unsupported, never a passing equality control.

For PID reuse, introduce a deterministic test-only barrier after connection attribution/request read and before the broker acquires its process handle. Let opener A pass its client handle to B, close all A process references, and exit. With the old implementation, churn until C actually receives A's Wine PID, then release the barrier and demonstrate the wrong attribution; bound the test and report inability to force reuse as inconclusive, not PASS. With retained opener references, assert that A's object/ID remains reserved, the original process is signaled dead, and the request denies despite B keeping the pipe alive. Add an injected wrong-object reply from the private query to verify CompareObjectHandles rejects even equal-SID/equal-logon peers. Repeat with death after the initial pin and during consent, when caller handles already prohibit reuse. Do not use an advisory PID substitution as evidence for this race.

For impersonation, obtain the caller's own restricted token using the sequence in (b), verify it is installed, and connect/write while impersonating. The hardened result must be ERROR_ACCESS_DENIED before consent, even with equal SID/authentication/session. Repeat with an ordinary same-identity duplicate to verify the conservative no-explicit-thread-token policy is intentional and visible.
